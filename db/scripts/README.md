# db/scripts — 数据级操作

这个目录放**数据操作**,与 `db/migrations/` 的**结构变更**分开。

区别在于:

| | `db/migrations/` | `db/scripts/` |
|---|---|---|
| 改什么 | 表、函数、视图、策略、权限目录 | 表里的**行** |
| 镜像 | 必须同步更新 `db/tables` / `db/functions` / `db/views`,`check_mirrors.py` 会查 | **不涉及镜像** —— 镜像描述结构,不描述数据 |

## 【安装种子表:脚本一律不许写】(OPS-1)

上面那句"脚本不涉及镜像"要继续成立,靠的是一条边界:**脚本碰不到任何被镜像逐行跟踪的表**。

`check_mirrors.py` 的 `SEED_TABLES` 列出的就是这些表 —— 目前是
`permissions`、`currencies`,以及 `accounts` 中 `is_system = true` 的那些行。
它们的判据只有一句话:**操作员能不能通过应用的正常使用改动这些行?**
不能,就说明这些行与代码版本绑定 —— 一个权限码只有在有代码去检查它的时候才有意义,
一个科目只有在有函数点名它的时候才必须存在。

因此:

- **这些表只许迁移写。** 数据脚本要改它们,那件事本身就不是"纯数据",它需要一次迁移。
- 迁移改了它们,就要**在同一个提交里更新对应的镜像种子** —— 与改表结构同一条规矩。
- 其余的种子表(`roles`、`role_permissions`、`leave_types`、`public_holidays`、
  `review_rating_scale`,以及三张单行配置表)是**运行期配置**:界面上改得动,
  所以线上与镜像不一致是**正常的**,`check_mirrors.py` 不比对它们。
  镜像里的那份是**全新安装的默认值**,脚本照旧可以随便写,照旧不涉及镜像。

**这条规矩是怎么来的**:`data.view_banking`(perm3)与 `data.view_sales`(perm3b)
两个权限码只写进了迁移,没写回 `db/tables/permissions.sql`;perm2a 把 `module.<m>`
一分为二时,镜像也停在了旧的 13 个未拆分码上。`check_mirrors.py` 当时只比结构不比数据,
于是一路是绿的。真正吓人的不是那两个码,是同一个盲区下的另一件事:
**照镜像重建出来的库,`accounts` 一行都没有,整个财务模块过不了任何一笔账。**
| 幂等 | 一次性,按日期命名 | 尽量写成可重跑的(`ON CONFLICT` / 先删后插 / 用带守卫的函数) |

**为什么值得单独存档,而不是在 SQL Editor 里手敲一次了事**:像角色与授权这种东西,
"为什么是这么授的"比"授了什么"更难重建。脚本连同它的注释一起进仓库,
于是理由留在了案发现场,状态也可以照着重放一遍。

**这里的脚本不会被 `check_mirrors.py` 检查**,因为它比对的是目录结构与镜像文件,
和行数据无关。脚本正确与否靠它自己末尾的验证查询证明。
