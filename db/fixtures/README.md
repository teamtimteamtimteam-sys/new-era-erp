# db/fixtures —— 行为断言(第三个判词)

`verify_rebuild` 问"这个仓库建得出库吗、结构与线上一致吗";这里问的是另一个问题:
**建出来的库,跑起来对不对。** 两者的关系,与 check_mirrors 之于 verify_rebuild 相同。

## 怎么跑

`db/gate.py` 在【本地重建】上逐个执行本目录的 `*.sql`,任何一个失败 → 判词
【行为断言】不通过,**退出码 4**,门就是红的。不是打印一行让人自己看见 ——
这条区别就是这套东西存在的全部理由。

单独跑一个:

```
psql "$DSN" -X -v ON_ERROR_STOP=1 -f db/fixtures/<name>.sql
```

## 为什么跑在【重建库】上,而不是线上

生产就是一次重建。而且重建库【没有任何业务数据】—— 没有客户、供应商、员工、批次。
于是"每个用例自带数据"不是靠人自觉,是环境逼出来的:你无处可借。

## 写法四条

1. **断言不变量,不断言字面量。** 「转正不碰假期账」比「余额等于 14」活得久。
   确实以某个数字【本身】为断言对象时(例如 4,838.71),就断言它,并在文件里
   写清楚这个数是怎么来的 —— 读的人重构不出来,早晚会把它"改对"。
   HR-2c 改了累积模型之后有两份 fixture 的期望值过期,先得判断"是过期还是回归"
   才敢动 —— 那次的代价就是这条规矩的由来。

2. **每个用例自带数据,不在用例之间重置。** 重置是又一件会做错的事。
   共享可变状态的用例会【因为错的理由通过】:同一张 PO 上跑两个用例,
   第二个"被拒"可能只是因为第一个已经把额度用掉了,与被测的规则毫无关系。
   (这不是假想:2026-08-05 的预付上限 fixture 就是这么骗过自己的。)

3. **失败必须让【门】红,不是打印一个不一样的字符串等人注意到。**

4. **只依赖【稳定的】引导数据,绝不依赖【随时间过期的】引导数据。**
   * 稳定:科目表、币种、角色与权限、假期类型、评级表 —— 它们不会因为日历翻页而失效;
   * 时间相关,**目前有两处**:
     - `public_holidays` 只播到 2026 年 —— 跨年之后依赖它的 fixture 会在一月的
       某个早上突然变红,而代码一个字没改;
     - `finance_settings.locked_before` 是操作员随月结推进的**运行时状态**。
       写这套 fixture 的当天它是 2026-08-01,于是一个用六月日期的用例当场
       PERIOD_LOCKED —— 不是被测规则错了,是 fixture 依赖了会动的东西。
       要它是什么,就自己 `UPDATE` 成什么(整段回滚,不影响任何人)。
   要用哪一天是假日,**fixture 自己插那一行**,别指望引导数据里有。
   与第 1 条同源:都是"不要依赖会过期的东西"。

## 权限:自建角色,不借引导角色

每个 fixture 自己建一个带【全部权限】的角色,配一个自选 uuid,再
`set_config('request.jwt.claims', ...)`。这样不依赖某个引导角色恰好有哪些权限。

> **与 docs/known-issues.md 的交叉引用 —— 这里靠的是一个已记录的【缺陷】。**
> `user_roles.user_id` 没有指向 `auth.users` 的外键,所以可以插一个不存在的 uuid。
> 那条缺陷一旦被修(补上外键),**本目录所有 fixture 会同时失败** ——
> 届时改为在 `auth.users` 里建一行临时用户即可。修那个缺陷的人请一并改这里;
> known-issues 那条也反向指着本文件。
