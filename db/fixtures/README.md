# db/fixtures —— 行为断言(第三个判词)

`verify_rebuild` 问"这个仓库建得出库吗、结构与线上一致吗";这里问的是另一个问题:
**建出来的库,跑起来对不对。** 两者的关系,与 check_mirrors 之于 verify_rebuild 相同。

## 怎么跑

`db/gate.py` 在【本地重建】上逐个执行本目录的 `*.sql`,任何一个失败 → 判词
【行为断言】不通过,**退出码 4**,门就是红的。不是打印一行让人自己看见 ——
这条区别就是这套东西存在的全部理由。

单独跑一个:

```
psql "$DSN" -X -v ON_ERROR_STOP=1 -f db/fixtures/<name>.sql
```

## 为什么跑在【重建库】上,而不是线上

生产就是一次重建。而且重建库【没有任何业务数据】—— 没有客户、供应商、员工、批次。
于是"每个用例自带数据"不是靠人自觉,是环境逼出来的:你无处可借。

## 写法四条

1. **断言不变量,不断言字面量。** 「转正不碰假期账」比「余额等于 14」活得久。
   确实以某个数字【本身】为断言对象时(例如 4,838.71),就断言它,并在文件里
   写清楚这个数是怎么来的 —— 读的人重构不出来,早晚会把它"改对"。
   HR-2c 改了累积模型之后有两份 fixture 的期望值过期,先得判断"是过期还是回归"
   才敢动 —— 那次的代价就是这条规矩的由来。

2. **每个用例自带数据,不在用例之间重置。** 重置是又一件会做错的事。
   共享可变状态的用例会【因为错的理由通过】:同一张 PO 上跑两个用例,
   第二个"被拒"可能只是因为第一个已经把额度用掉了,与被测的规则毫无关系。
   (这不是假想:2026-08-05 的预付上限 fixture 就是这么骗过自己的。)

3. **失败必须让【门】红,不是打印一个不一样的字符串等人注意到。**

4. **只依赖【稳定的】引导数据,绝不依赖【随时间过期的】引导数据。**
   * 稳定:科目表、币种、角色与权限、假期类型、评级表 —— 它们不会因为日历翻页而失效;
   * 时间相关,**目前有两处**:
     - `public_holidays` 只播到 2026 年 —— 跨年之后依赖它的 fixture 会在一月的
       某个早上突然变红,而代码一个字没改;
     - `finance_settings.locked_before` 是操作员随月结推进的**运行时状态**。
       写这套 fixture 的当天它是 2026-08-01,于是一个用六月日期的用例当场
       PERIOD_LOCKED —— 不是被测规则错了,是 fixture 依赖了会动的东西。
       要它是什么,就自己 `UPDATE` 成什么(整段回滚,不影响任何人)。
   要用哪一天是假日,**fixture 自己插那一行**,别指望引导数据里有。
   与第 1 条同源:都是"不要依赖会过期的东西"。

5. **前提要显式设定,哪怕默认值恰好是对的。**
   一个 fixture 只要依赖某个前提,就自己把它设成需要的样子 —— 不要因为
   "现在的默认值刚好合用"就不写。默认值合用是【偶然】,而偶然会过期:
   下一个 fixture 在同一个重建库里把它改了,或者引导值哪天变了,
   你的用例就会因为一个与被测规则无关的原因红掉(或者更坏:绿掉)。
   
   具体到今天:每个 fixture 都显式写 `UPDATE finance_settings SET locked_before = ...`,
   即便它设的就是 NULL;要用哪天是假日,自己插、并先清掉窗口内的既有假日。

   **例外分支:被数据库强制保证的不变量,可以【断言】而不是【设定】,但必须写明理由。**
   累积费率就是这样:`guard_effective_accrual_rate` 不许改动已生效的费率
   (HR-2c 立的规矩,改只能加更晚生效的新行),所以它读起来是安全的。
   fixture 04 曾试图 DELETE 重设,当场被那条守卫拒掉 —— 于是改为读 + 自证前提
   (两类费率必须确实不同),并把"为什么这里可以读"写在旁边。
   **判断标准:你能指出一条强制它不变的守卫吗?能就断言,不能就设定。**

## 权限:自建角色,不借引导角色

每个 fixture 自己建一个带【全部权限】的角色,配一个自选 uuid,再
`set_config('request.jwt.claims', ...)`。这样不依赖某个引导角色恰好有哪些权限。

> **与 docs/known-issues.md 的交叉引用 —— 这里靠的是一个已记录的【缺陷】。**
> `user_roles.user_id` 没有指向 `auth.users` 的外键,所以可以插一个不存在的 uuid。
> 那条缺陷一旦被修(补上外键),**本目录所有 fixture 会同时失败** ——
> 届时改为在 `auth.users` 里建一行临时用户即可。修那个缺陷的人请一并改这里;
> known-issues 那条也反向指着本文件。

## 第 6 条:断言【可见性】的臂,必须自己切数据库角色

**fixture 以 `postgres` 跑,而 `postgres` 是超级用户 —— RLS 对它完全不生效。**
所以任何一条"某某读者【看不见】这一行"的断言,不切角色就是在证明空话:

```sql
EXECUTE 'SET LOCAL ROLE authenticated';   -- 读之前
SELECT ... INTO v_x FROM some_view WHERE ...;
RESET ROLE;                                -- 读之后
```

`has_permission()` **不需要**切角色 —— 它是 SECURITY DEFINER,按
`request.jwt.claims` 里的 sub 解析,与数据库角色无关。**这正是最容易骗过自己的地方:**
靠 `has_permission()` 的臂(属主权限视图的谓词、函数里的 `require_permission`)
不切角色也是真的,靠 RLS 的臂不切角色就是假的,而两者在代码里长得一模一样。

fixture 26 第一版就栽在这里:A、C 两臂靠 RLS,没切角色 —— 把
`processing_run_allocation_status` 改回 invoker 注入故障后,gate 的 `xmodule`
判词红了,**这份 fixture 依旧绿**。与 FIN-30 那条空转的第三臂同一种病。

### 已经查过了:01–25 全部【不受影响】(OPS-14 后的普查,2026-08-09)

不必再查一遍,结论与证据都在这里:

* **25 份 fixture 全部只建【一个】角色,并且 `SELECT code FROM permissions` 授全部权限**,
  各自只调一次 `set_config('request.jwt.claims', ...)`,零处 `SET LOCAL ROLE`。
  **没有第二个读者、也没有受限读者,可见性断言在结构上无从写起。**
* 全库 SELECT 策略无一条是 RESTRICTIVE(0 条),没有"开了 RLS 却没有 SELECT 策略"的表,
  没有 FORCE RLS。**策略全是 PERMISSIVE(OR 语义),所以持全部权限的读者一律全见。**
* 线上实测:130 张表/视图,`postgres` 与 `authenticated`(持全部权限)**行数零差异**;
  其中 106 张再比【全列内容指纹】,**同样零差异**。另外 24 张比不了 ——
  被【列授权】挡住,那是 colgrant/colreader 的地盘,不是 RLS。
* 25 份里期待的 24 种拒绝,**全部是函数/触发器/CHECK 抛出的具名业务错**
  (`PERIOD_LOCKED`、`ALLOC_EXCEEDS`、`TEMPLATE_CURRENCY_MISMATCH` …),
  **没有一条是权限错或 RLS 拒绝** —— 所以也不存在"靠 RLS 拒绝"的臂。
* 双向故障注入(scratch 库):把 5 个被 fixture 读到的视图【全部改回 invoker】,
  01/10/18/19/24 **依旧全绿**,只有 26 变红 —— 26 是唯一的可见性断言;
  反过来给这 5 个臂各注入【它自己该抓的那个故障】(ar 的已结额不再相减、
  拿掉 `holiday_calendar_missing` 支、拿掉 `price_history` 过期源、
  回收率丢掉产出边、拿掉 `system_start_not_set` 支),**五个全部按名报红** ——
  它们绿得有理由,不是空转。

**真正的结论不是"都没事",而是:这套 fixture 里只有 26 一份在测权限行为,
OPS-14 之前是零份。** 下一份涉及"谁看得见什么"的 fixture,按本条写。
