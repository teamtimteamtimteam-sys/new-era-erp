2026-09-02。本刀**不转换任何页面** —— 187 个已上线页面一个像素都没有变,
而这一条是**证出来的**(见文末「怎么证的」)。没有 DDL。

BRAND-1 装了九个 shadcn 组件与品牌 token,IA-BUILD-1 搭了外壳(九个模块、面包屑、
dock、淡底、浮动层的磨砂)。本刀是**页面底下那一层**:一个按钮按下去有什么反应、

逐个模块的页面转换**不在本刀里**。

## 〇 · 先更正三件事(EXISTENCE FIRST)

委托书要求"三次连着的刀都发现机制已经在了 —— 去查,别假设"。查了,三条里有两条要更正。

### ① 「九个组件零采用」——**错的,是我自己第一次量错了**

第一次用 `grep "components/ui/button\""` 量,得到 0 采用。**那个 grep 要求双引号**,

也就是说 **`/login` 是一个真的、已上线的、已经转换过的页面**(LOGIN-1 做的)。

### ② FE-0 的「排序:一个都没有」——**结论错,而它的数没错**

FE-0 写的是「`sortBy` / `sortKey` / `sortDir` / `toggleSort` 全仓库 0 次命中」,
**这句话是对的**。它由此推出「用户在任何一张表上都不能点表头重排」,而**这一步错了**:

|---|---|---|
| 用户可改的排序 | **0** | **8 页**:/inbound · /materials · /output · /customers · /suppliers · /processing · /metal-prices · /finance/fx |
| 用户可用的分页 | 「局部有,大部分没有」(28 处 `.range()`) | **17 页** |
| 列显隐 | **0** | **0** ✓ FE-0 说对了 |

**这不是吹毛求疵,它改了组件的形状** —— 见 §1「两种排序模式」。

### ③ 「201 张表是不是三类形状」——**不是三类,是一类**

逐张解析 201 个 `<table>` 块(161 个文件,与 FE-0 的数一致):

| | |
|---|---|
| **会重复的账簿**(块里有 `.map`) | **198 / 201** |
| 静态明细表 | **3** |
| 列数分布 | 2–4 列 **58** · 5–6 列 **88** · **≥7 列 52** |

**结论:一种答案可以覆盖全部。** 它们不是「账簿 / 两列明细 / 摘要」三类,

## 一 · 表格:`app/components/ui/data-table.tsx`

### R3 · 手机上的画法:【留下的列 + 一行展开】

**不是卡片流。** 一张账簿存在的意义是**顺着一列往下比** ——
60 行变成 60 张卡片之后,那件事就再也做不了了。卡片流是最常见的响应式答案,
而它恰好毁掉这张表唯一不可替代的能力。

**也不是只给横向滚动。** 那是把桌面版缩小,R3 明确不要。

所以:手机上留下**声明过的那几列**(身份 + 那个要紧的数),
其余的收进每行左边那个「›」,点开是一段带标签的 `<dl>`。

**列的优先级每张表自己声明,组件不猜。**
「猜前 N 列」在有些表上一定挑错:/inbound 的前三列是批次号、物料、供应商,
而人在手机上要找的是**批次号、物料、余量** —— 供应商要让位。

> **没有声明 priority 的表,组件【当场按名拒绝】**(`DATATABLE_NO_PHONE_COLUMNS`),
> 而不是默默退回「前 N 列」或「横向滚动」。
> 本仓库对这个形状有一长串先例:不声明重量基准就拒、缺一个交易日就拒、
> 没录上限就拒绝作判断。**一次响亮的拒绝,好过一个悄悄挑错列的默认值。**
> 它拒得起,是因为本刀没有转换任何页面:今天没有一个页面会碰到这条路,
> 而每一次转换都会在第一次渲染时就撞上它。

### R4 · 四个能力,默认【全关】

排序 / 筛选 / 分页 / 列显隐都是显式开关,默认 false。
**把组件换上去不会让任何一页凭空多出一个控件** —— R4 要的就是这个。

### ★ 两种排序模式 —— 「永不声称排了它没拿到的东西」

失败模式是静默的:一页只取了一屏数据,却给出一个排序控件;
人按下去,以为看到的是**全体里最大的那个**,其实只是这一屏里最大的。

处置**放在类型上**,而且比"提示一句"更硬:

```ts
type SortingClient = { sorting: { mode: 'client'; coverage: 'complete' } }
type SortingServer = { sorting: { mode: 'server'; coverage: Coverage
                                 active: …; href: (key, dir) => string } }
```

* `mode: 'client'` —— 组件自己排。**类型上只接受 `coverage: 'complete'`。**
  拿到的是一部分,就**打不开它** —— 编译期就打不开。
  一句提示要人去读;一个类型错误不需要任何人记得。
* `mode: 'server'` —— 表头渲染成**链接**,由页面已有的 URL 参数去数据库排。
  **这一档是为上面那 8 页 / 17 页留的路**:它们的排序是在数据库里对**全体**排的,
  换成客户端排序**是一次降级**,而且正好是上面那个静默失败。
  这时候排序看得见全体,所以**不出警告**,只报"这一屏几行 / 全体几行"。

> 也就是说:**转换刀不必为了用上这个组件而放弃已经正确的服务端排序。**

### 不引 TanStack Table —— 和前两次同一条标准

BRAND-1 拒 shadcn 的 data-table 时说的是「data-table 不是一个组件 ——
排序与列显隐是**缺失的功能**,不是样式」。本刀同意,并按同一条标准判这个依赖:

* 我们要的四件事,对着**已经在内存里的、一页大小的**数组,各是一个比较器、
  一个谓词、一次 slice、一个 `Set`;
* TanStack 真正值钱的地方(服务端分页、虚拟滚动、分组、faceted filter)**我们刻意都不要**;
* 它**完全不碰**这一刀最难也最值钱的那部分 —— 390px。那部分无论如何要手写;
* 而采用它意味着 201 张表在转换时都要改写成 `columnDef` 形状 ——
  **那是比"换掉标记"大得多的迁移面**。
* 列描述符两边都要有(priority 是每张表声明的),而我们这一份可以小、
  并且是**照着手机形态设计**的,TanStack 那一份不是。

### 390px 实测(不是断言)

真浏览器(chrome-headless-shell + CDP)、真服务端渲染、真会话,量的是 `getComputedStyle`
与 `scrollWidth`,不是看截图:

| | 390 × 844 | 1280 × 900 |
|---|---|---|
| 页面横向溢出 | **无**(390 ≤ 390) | **无**(1280 ≤ 1280) |
| 表格 scrollWidth / clientWidth | **342 / 342**(是**放得下**,不是滚动) | 1260 / 1260 |
| 13 列里看得见 | **3 列**(批次号 · 物料 · 余量)+ 展开钮 | **13 列** |
| 点开一行 | `aria-expanded=true`,`<dl>` 出现,**其余 10 列全部拿得到**,**仍然不溢出** | — |

**实测逼出来的两条改动**(都记下来,因为它们不是设计出来的,是量出来的):

1. **手机上用 `table-fixed`,桌面上恢复 `auto`。**
   auto 之下任何一个格子都能把整列撑宽 —— 实测一枚「无库存 · out of stock」小片
   把第三列撑到 260px,把物料那一列挤成**每行一个字**。
   只剩三列的宽度里,一个格子无权决定整列宽度。
2. **表头桌面上不折行(`sm:whitespace-nowrap`)。** 实测 1280px 下「库存状态」
   被折成每行一个字。手机上**不加**这一条:那里是 table-fixed,nowrap 会顶出格子。

## 二 · 动效清单 —— 四条,全部为状态服务

R1:**动效只用来反馈状态,永不装饰。** 这是一个一天用八小时的工具;
入场动画、页面转场、会跳的按钮,到第三天只剩烦人,还会让页面**感觉**比实际慢。
下面四条就是全部 —— 没有第五条。

| 状态 | 画法 | 写在哪 | 为什么这个状态值得反馈 |
|---|---|---|---|
| **成功** | 一次扫过的浅绿,1.1s 退回原样 | CSS `@keyframes base-flash-ok` | 写完之后屏幕上常常什么都没变(数字本来就是那个数),于是分不清「存好了」和「点漏了」 |
| **校验失败** | 红边 + 两下 3px 横向推移,260ms | CSS `@keyframes base-nudge-err` | 焦点常常不在出错那一格;颜色是静态的,一次极短的位移把眼睛**带过去** |
| **加载中** | 低振幅骨架脉冲(1 → 0.55)· 按钮转圈 | CSS `@keyframes base-skeleton` / `base-spin` | 「在取数」和「取回来是空的」在屏幕上一模一样;而按下去没反应的按钮会被**再按一次**(IA-BUILD-1-fu1 那条缺陷的原文) |
| **数字变了** | ~15 行 `requestAnimationFrame`,easeOutCubic,420ms | **JS**(`feedback.tsx` 的 `CountUp`) | 一个总数悄悄从 812 变成 1,043,和它一直是 1,043,在屏幕上一样 |

外加一条**过渡**(不是动画):`base-pressable` —— 按下的即时回应。
R1 说得明白:**按下去是什么反应,是按钮自己的性质**,不是事后洒上去的东西。

### 减弱动效:关掉的是【动】,不是【状态】—— 实测

**把状态本身也一起关掉,是把可访问性偏好读成了「这个人不需要知道结果」。**

实测方法:CDP 模拟 `prefers-reduced-motion`,把六个类各挂到一个注入元素上,
读 `getComputedStyle` 的 `animation-name` / `transition-property`。
**直接量 CSS,不依赖"点一下按钮看它有没有动"** —— 后者要靠某次交互恰好发生。

| 类 | no-preference | reduce | |
|---|---|---|---|
| `base-flash-ok` | `base-flash-ok` | **`none`** | ✓ |
| `base-nudge-err` | `base-nudge-err` | **`none`** | ✓ |
| `base-skeleton` | `base-skeleton` | **`none`** | ✓ |
| `base-spin` | `base-spin` | **`none`** | ✓ |
| `base-reveal` | `base-reveal` | **`none`** | ✓ |
| `base-pressable` | `background-color, transform` | **`none`** | ✓ |

**而状态一个都没丢**(同一次实测,量的是真实渲染出来的元素):

| | reduce 之下 |
|---|---|
| 骨架 | 仍在场、仍是 `rgb(229, 238, 244)`(`--brand-muted`),只是不再脉冲(opacity 固定 0.75) |
| 校验失败 | 仍是 `aria-invalid="true"`,边框仍是 `rgb(183, 91, 83)`(`--brand-destructive-fill`) |
| 按钮 pending | 仍 `disabled` + `aria-busy`,只是圈不转 |
| `CountUp` | 直接落在终值(JS 里读 `matchMedia`,不走 rAF) |

### 第二次拒绝 motion.dev —— 理由和 LOGIN-1 那次**不同**

LOGIN-1 拒它是因为 **CSS 25 行就够了**。这一次的理由更硬,两条:

1. 上面四种状态里**三种是 CSS 原生的**;第四种需要一个逐帧循环,
   而那是 **15 行 `requestAnimationFrame`,不是一个 40KB 的依赖**。
   **那 15 行就是 motion.dev 要顶替的全部东西。**
2. **更要紧的一条:** motion.dev 这一类库要么带全局样式、要么把组件包成它自己的元素,
   而 **BRAND-1 拒 tw-animate-css 正是因为它要一次全局 import** ——
   BRAND-1 的 187 页安全论证**整个建立在"不往全局加任何东西"上**。
   引它就等于把那条论证花掉,换四个 CSS 做得到的效果。

> 本刀自己加的那一个全局文件(`app/base-motion.css`)照 BRAND-1 的先例办:
> 新文件、只加不改、类名一律 `base-` 前缀,而 `base-` **作为类名**在本刀之前
> 全仓库 0 次出现(量过;`messages/en.ts` 里那 5 处 `base-currency` 是英文正文,不是类名)。
> 于是它们在声明级证明里全部落在「新增」那一栏。

## 三 · 拒绝态:一种画法替掉十几种

**词没有漂,漂的是颜色。** 精确量:`t('common.restricted')` **41 处、横跨 32 个文件**,
而直接包着它的元素上有 **12 种不同的 className 写法**(另有 14 处不直接落在标签上 ——
`title={…}` 或三元里的取值)。写法举例:`text-gray-400 italic` / `text-sm text-gray-600`(11 处)/ `text-gray-500` /
`font-mono text-xs` / 甚至 `text-3xl font-bold text-gray-300`。
于是**同一句话在不同页面上分量完全不同**:有的像一句正式的拒绝,有的像一行注释,
有的像忘了填。

`<Refusal>` 只做一件事:把那十几种收敛成一种(Tim 在 sampler 上指的变体 C,填充小片)。

**四个字眼共用一种颜色。** 各配一个颜色听着更"有信息",但那正是**十种画法当初长出来的方式**
—— 每一页各自决定这一句该有多重。**区分由词承担**(词没有漂),颜色只承担「这是一句拒绝」。
将来若真要分色,那要是一次集中的、看得见的决定,不是十页各挑一个灰。

### ★ 「替掉十种」在本刀里【只做到一半】—— 而这是 R5 与验收条件的直接冲突

验收条件写的是「**一种拒绝画法,替掉十种**」;R5 写的是「**本刀不转换任何页面**」。
这两条在这一项上**直接撞车**,因为那十种画法**不在页面里,在共享组件里**:

| 组件 | 今天的画法 | 被多少文件用 |
|---|---|---|
| `app/components/MaskedValue.tsx` | `text-gray-400 italic` | 8 |
| `app/components/ActorName.tsx` | `text-gray-500` | 7 |
| | | **合计 14 个文件** |

也就是说,**只要把这两个共享组件改成 `<Refusal>`,14 个已上线文件的样子当场就变了。**

**处置:R5 赢,并且照 BRAND-1 的先例把这个取舍写下来** ——
BRAND-1 遇到 R2(产品字体是 Google Sans)与 R3(不许改已上线页面)相撞时,
判的是 R3 赢:字体在取样页里加载、演示,全站切换留给一次单独的、看得见的决定。
这里逐字同一条:

* **本刀交付的是那一种画法本身** —— `<Refusal>` 建好、量过对比度、在取样页上
  与"今天的五种真实写法"并排画出来;
* **把 `MaskedValue` / `ActorName` 换过去,是转换刀的第一件事**,
  而且它是**性价比最高的一件**:改 2 个文件,14 个文件的拒绝态一次收敛。
* 这句话必须写下来,否则下一个人会以为收敛已经发生了 —— **它没有。**
  今天线上仍然是十几种写法。

### ★ 一处对变体 C 的修正(量出来的)

| | |
|---|---|
| 片内文字 `--brand-text` on `--brand-accent` | **12.59:1** ✓ AA |
| ★ 填充色 `#E1F5FF` **对着页底** `#F1F9FE` | **1.05:1** |

## 四 · 卡片与面板要不要磨砂 —— **建议不要**

R2 把这一条留给了判断(「淡底落地、看得出效果之后再说」)。判断如下:

**一张卡片不是浮动层。** 顶栏与 dock 是 sticky/fixed 的,页面内容**真的从它们底下滚过去**
—— 那正是磨砂要透出来的东西,IA-BUILD-1 也正是对着"合成色"量的那 0.90。
而一张卡片底下**什么都不经过**:它压着的就是那层淡底,一个不动的纯色。
于是磨砂**没有东西可以透出来**,却要为此降低卡片里每一个数字的对比度 ——
**付出了代价,买不到那个效果。**

> 但这是一个**看着才能定**的事,所以取样页 §④ 把两个都画出来了(实心白面 vs 与顶栏同一档的 0.90 磨砂)。
> **Tim 指哪个算哪个**;上面这段是默认值,不是结论。

### 输入框的推移为什么默认关着

这一条值得单独写,因为它是**第 〇 节那个量错**直接带出来的:

`/login` 是已上线的一页,而它两个输入框都写着 `aria-invalid={fieldsInvalid || undefined}`。
如果校验失败的推移**默认打开**,本刀就在一个已上线页面上改了行为 ——

## 十 · ★ BTN-1(2026-09-06):档位定下来了 —— 而【一个按钮不够】★

Tim 的裁定,一句话:**「一个看起来像普通动作的破坏性动作,是缺陷,不是不一致。」**
所以这一刀先定档位,再转换 —— 反过来做会把一个真实的区别抹平。

### 10.1 五个档位,以及【不靠颜色】怎么分开

| 档 | 什么时候用 | 底 | 字 | 边 | 字重 | 左竖条 |
|---|---|---|---|---|---:|---|
| `default` | 这一页存在的那个动作 | ocean 实底 | 白 | 无 | 500 | 无 |
| `secondary` | 列表控件 / 行内控件 / 取消 | 透明 | text | border-strong | **400** | 无 |
| `reversal` | 撤销一个**已过账**的状态 | 透明 | text | border-strong | 500 | **虚线 3px** |
| `destructive` | 真的销毁或作废一条记录 | destructive 淡底 | destructive-text | destructive/40 | 500 | **实线 3px** |
| `warning` | 系统在告诉你一件正在发生的事 | warning 实底 | 白 | 无 | 600 | 无 |

**★ 颜色是最后一条判据,不是第一条。** 一个只能靠颜色分辨的破坏性动作,
把最危险的那一格押在**一部分人根本用不了的信道**上。四条不经过颜色的判据:

1. **有没有实底** —— 只有 `default` 与 `warning` 是实心的。一个区域只该有一个实心钮。
2. **字重** —— `secondary` 是唯一的 400。它是唯一"更轻"的档。
3. ★ **左竖条** —— `destructive` 实线、`reversal` 虚线,**同一处几何,一实一虚**。
   别的档没有。这一条是纯几何,完全不读颜色。
4. **动词形状** —— `destructive` 是 Delete/Void;`reversal` 是 Un-/Re-。
   ★★ **而【动词形状是最不可靠的一条】,BTN-3 与 BTN-3b 各抓到过它说谎:**
   `fx/DeleteButton` 写着 Delete 做的是软删除;`RoleForm:166` 同样;
   `DecideControls:89` 写着 Cancel 做的是补一条等额反向记账。
   **判据永远是 handler 做了什么,不是脸上那个动词。**

> ### ★★ 作废 vs 撤销:这条界线 BTN-3b 之前【只是默契】,现在写下来 ★★

> 上面 destructive 那一格写着「真的销毁**或作废**一条记录」,而 `作废` 这两个字

### 10.2 ★ 撤销档为什么是一个真的档,不是 destructive 的一种写法 ★

实测 **57 个按钮**做的是"撤销一个已经过账的状态":`Reopen` · `Unpost` ·
`Unapply` · `Unreconcile` · `Unmatch` · `Turn GST off`。**它们不删任何东西,

### 13.6b ★ 一次量出来的【转换代价】:`shrink-0` 让每一个转过来的按钮在窄的 flex 行里【压不动了】

**版式探针在 `/logistics/lanes` 上报了 +41px,而点名的元凶是【一个库按钮】** ——
也就是本刀刚转过去的那一个。这一处做了 A/B,因为"是不是我弄的"只能靠量:

| | 390px 的溢出 | 元凶 |
|---|---:|---|
| 本刀之前(从备份还原那一个文件) | **+15px** | `button.rounded bg-blue-600 px-3 py-1 …`(手写钮) |
| 照原样转换 | **+41px** | `button.group/button …`(库按钮) |
| 加上 `shrink whitespace-normal` | **+12px** | `form.flex items-end gap-2 …`(表单自己,与按钮无关) |

**机制,读代码读出来的:** 库的基础层写着 `shrink-0` 与 `whitespace-nowrap`,
两条都是**刻意的** —— 一个被挤扁、文字被截断的按钮比一个溢出的行更坏。
而这三张表单是**不换行的 flex 行**,手写钮当年**可以被压缩、也可以折行**。
于是转换在这一页上**把一个可压缩的东西换成了一个不可压缩的东西**。

> ★ **这不是"库写错了",是【转换有代价,而代价要量】。**
> `size` 反而更小(`px-3`→`px-2.5`、`text-sm`→`text-[0.8rem]`),
> 光看内边距会得出"应该更窄"的结论 —— **而它更宽,原因在两条与尺寸无关的类上。**

**处置:在这四个调用点解开这两条**(`shrink whitespace-normal`)。
它是**这一行的版式性质**,不是档位性质,所以留在调用点是对的
(与 BTN-2 §12.4b 反对"在 26 个调用点各写一遍 `font-normal`"不矛盾:
字重属于档位,能不能被压缩属于它所在的那一行)。

★★ **给 BTN-3b 的一句话,因为这条对【每一次】转换都成立:**
> **把一个手写钮转进一个不换行的 flex 行之前,先在 390px 上量一遍。**
> `shrink-0` + `whitespace-nowrap` 是库的两条硬性质,而它们只在窄屏上显形。

顺带记下这一轮版式探针的全貌(19 条路由,**全部是本刀改过的页**):
**可用 16 / 19**;三处 U1 不过 —— `/operation/processing/new` **+416px**、
`/purchasing/payment-terms/new` **+257px**(两处元凶都是**手写 `<select>`**,
与按钮无关,BTN-2 已经把前者立过案)、以及上面那处 `/logistics/lanes` **+12px**。
一处 U2 不过(`/purchasing/payment-terms/new` 一张表被非滚动祖先裁掉)。
**这三处一处都不是本刀造成的,而 `/logistics/lanes` 本刀让它【好了 3px】。**

### 17.3 ★★ 一条量出来的库缺陷:`asChild` 在这棵树上【从来没有能用过】★★

```
⨯ Error: Slot failed to slot onto its children.
  Expected a single React element child or `Slottable`.
```

原因在 `button.tsx` 里,一行:

```jsx
{busy && (<span … />)}     ← busy 为 false 时,这一项求值成 `false`
{children}                 ← 而 `false` 仍然【是一个 children 数组元素】
```

`asChild` 那条路上 `Slot` 收到的是**两个**孩子,而它只接受一个。

> ★ **所以「零调用点」不是"没人想到用",是"用了就红,于是没有人留下过一个"。**
> 这正是委托书那句「`asChild` 零调用点,所以没有任何东西验过它」的直接后果:
> **一个没有调用点的能力,和一个坏掉的能力,在任何检查的退出码上都是同一个字节。**
> ☞ 而 `npm run build` **绿着** —— 这些页是按需服务端渲染的,构建期不执行它们。
>   **抓到它的是 390px 那一支,不是构建,也不是任何一道闸。**

**修法**(§八(b):库里缺能力就先修库):`pending` 时才构造那个 fragment,
否则**原样传 `children`**。非 `asChild` 且非 pending 那条路**渲染结果一个字节没变**
(`{false}{children}` 与 `{children}` 画出来的 DOM 相同),187 个已转按钮不受影响。

### 18.1 ★★ 判据:这一段【原样抄进来】,因为它决定每一处的档位 ★★

> **WHERE IT SITS DECIDES WHAT THE BUTTON LOOKS LIKE.**

### 19.3 动作槽的容器 —— 以及 shrink-0 那条诊断【只对了一半】

**记录在案的诊断(BTN-5b):**「库按钮基础层带 `shrink-0`,压不扁。」
`shrink-0` 确实在(`button.tsx:63`),而**只把它拿掉,一个像素都不会变。**

一个 flex item 要能变窄,**三件事都得成立**:

| | 条件 | 基础层的实况 |
|---|---|---|
| ① | `flex-shrink ≠ 0` | `shrink-0` —— 挡住 |
| ② | `min-width` 能低于 min-content | flex item 默认 `min-width:auto` —— 挡住 |
| ③ | 字里有可断行的地方 | `whitespace-nowrap` —— 挡住,于是 min-content = 内边距 + **整条标签** |

☞ 拿掉 ① 之后 ② 与 ③ 照旧,宽度纹丝不动。
**而它取代的那个裸 `<Link>` 没有 nowrap** —— 它的 min-content 只是【最长的那个词】,
所以它能折到第二行。**转换真正夺走的是折行能力,不是收缩能力。**

**因此不改按钮,改【行】。** 让按钮可收缩 = 让它压扁或裁掉自己的标签,
而 `survey-phone` 的 `clipped` 正是为抓这种事而存在的 —— 那会在某一刀之后
变成一桩新悬案。让行折,则每个按钮保持自然宽度,溢出变成第二行。
★ **`whitespace-nowrap` 与 `shrink-0` 对按钮都是对的,`button.tsx` 因此一个字没动。**

**三次量出来的溢出,就是这条修法的证据:**

| 刀 | 路由 | 溢出 |
|---|---|---|
| BTN-3 | 某一行 | +15 → +41 |
| BTN-5a | `/finance/bank` | 39 → 168 |
| BTN-5b | `/suppliers` | 0 → 20(两条链接因此退回) |

#### 19.3a 【那个"共用容器"根本不存在】—— 而这是本刀改动的真正理由

委托书问「修在共用的 ListPage 动作容器里,还是修在按钮里」。**实测:两个都不成立。**
`actions` 是一个调用点自己传的 `ReactNode`,**外壳只是把它原样放进抬头行**。

普查(TypeScript AST,`app/**/*.tsx`):**103 个 `<ListPage` 调用点 / 100 个文件,
其中 47 个传了 `actions`,而它们用了 12 种互不相同的写法:**

| 写法 | 处数 | 备注 |
|---|---:|---|
| 裸 `<Button>` | 24 | 直接成为抬头行的 flex item |
| 三元表达式 | 5 | |
| `<span/>` | 5 | 占位 |
| `<div className="flex gap-2 shrink-0">` | 4 | ★ **那个 shrink-0 正好把折行堵死** |
| `<div className="flex items-center gap-3">` | 2 | |
| `<div className="flex flex-wrap items-center gap-3 justify-end">` | 1 | ★ 有人已经独立发现了正确形状 |
| 裸 fragment `<>` | 1 | ★ **F4 的 `/finance/fx` 就死在这上面** |
| `<div className="flex gap-3">` · `<div className="flex gap-2">` · `<Link>` · `<form>` · `<DeleteButton/>` | 各 1 | |

**抬头行自己【早就】是 `flex flex-wrap`** —— 会溢出的从来不是它,
**是调用点各自搭的那一层**。所以本刀建的不是"改一个共用容器",是**把那个
一直被假设存在、其实不存在的容器建出来**:

```jsx
{actions && (
    <div className="flex flex-wrap items-center justify-end gap-3">{actions}</div>
)}
```

四处 `shrink-0` 一并撤掉(`/inventory/reports/{snapshot,ledger,safety,violations}`,
四处形状逐字相同:两个 outline/sm 的 CSV / PDF 导出钮)。**逐个读过,
没有任何一处的 `shrink-0` 有折行之外的理由。**

#### 19.3b ★ 那条「基线参照会不会移位」的风险,是【量】掉的,不是【想】掉的

抬头行是 `items-baseline`。此前一个裸 `<Button>` **自己**就是 flex item,
标题与按钮按【按钮的基线】对齐;包一层之后 flex item 变成了那个 div。
CSS 说 flex 容器的基线取自它第一个 flex item —— 也就是**应该**没有变化。
**而"应该"不是一个测量结果**,所以本刀为它建了一支探针
(`scripts/probe-header-baseline.mjs`,普查不是闸):
用 `Range.getClientRects()` 取【标题文字】与【按钮标签文字】各自的墨迹盒,
比 `delta = 标题墨迹底边 − 按钮墨迹底边`,两个宽度各量一遍。

**结果(390 / 1280,改前 → 改后):**

| 路由 | 形状 | 390 delta | 1280 delta | 抬头高 390 | 抬头高 1280 |
|---|---|---|---|---|---|
| `/materials` | 裸 `<Button>` | 2 → **2** | 2 → **2** | 35 → 35 | 35 → 35 |
| `/sales/orders` | 裸 `<Button>` | 2 → **2** | 2 → **2** | 35 → 35 | 35 → 35 |
| `/hr/departments` | 裸 `<Button>` | 2 → **2** | 2 → **2** | 35 → 35 | 35 → 35 |
| `/purchasing/orders` | 裸 `<Button>` | −35 → **−35** | 2 → **2** | 72 → 72 | 35 → 35 |
| `/inventory/reports/ledger` | 撤掉 shrink-0 的 div | 2 → **2** | 2 → **2** | 33.59 → 33.59 | 33.59 → 33.59 |
| `/suppliers` | ★ 本刀转了两条链接 | −39 → −32.41 | 2 → **2** | 80 → 112 | 35 → 35.59 |
| `/finance/fx` | ★ 本刀改了顺序 | 2 → −34.41 | 2 → **2** | 71 → 72 | 35 → 35.59 |

★ **四条裸 `<Button>` 路由 + 那条撤掉 shrink-0 的,`delta` 与抬头高在两个宽度上
逐字未变。那条风险的代价实测是零。**
动了的两条正是**本刀故意改了内容**的两条(两条链接变成按钮 / 次主顺序对调),
而它们在 1280 上 `delta` 仍然是 2 —— 变的是行高(390 上多折了一行),不是基线。
