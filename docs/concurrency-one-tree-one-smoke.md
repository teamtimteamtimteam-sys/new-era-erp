# 一棵树,一次一个冒烟;一棵树,一个 Claude 会话

> 这份笔记写在仓库外,是【故意的】:写它的时候另一个会话正要提交同样五个文件,
> 一个新的未跟踪文件会被它的 `git add` 顺手扫进去 —— 那正是本文要讲的那种事故。
> 内容可原样搬进 `docs/`,等那次提交落地之后。
> 发现于 2026-08-10 夜,HEAD ef5f4de(REACH-1 那一刀),两个并行会话同跑一棵树。

## 机制:两处并发不安全,都不是偶然

`scripts/smoke-routes.mjs` 有两个地方【假定了自己是这棵树上唯一在跑的那个】。

**一 · `sweepScratch()` 无差别删除。** 它在【每次启动时】删掉所有
`smoke-*@test.local` 账号与全部 scratch 员工行 —— **不看归属,不看年龄**:

```js
const stale = (page?.users ?? []).filter((u) =>
    (u.email ?? '').startsWith('smoke-') && (u.email ?? '').endsWith('@test.local'))
```

对"上一次跑挂了留下的残骸"这是对的,也是它存在的理由。但它分不出
"上一次的残骸"和"另一个进程【此刻正在用】的账号"—— 两者长得一模一样。
于是后启动的那个,一上来就删掉先启动的那个的会话账号,
而先启动的那个会在下一次 `fetch` 时拿到一片 401,报出来的却是路由失败。

**二 · `const PORT = 3199`。** 硬编码常量,不读环境变量。第二个 `next dev` 拿到
`EADDRINUSE`,直接退出 —— 这一半反而是【好的】:它响亮地失败,
而 sweep 那一半是【安静地】把对方弄坏。安静的那个危险得多。

数据库是共享的 live 库,所以【换端口也救不了】。两个冒烟不能同时正确,句号。

## 实况:双方都在"清理残留",双方都是对的

值得记下来的不是结论,是这个序列 —— **没有任何一步是错误操作**:

1. 会话 B 起冒烟,拿到 3199,日志写 `/tmp/reach_clean.log`。
2. 会话 A 起冒烟,命令里带 `rm -f /tmp/reach_clean.log` —— 把 B 正在写的文件
   **unlink 了**。B 的 fd 还开着,继续往一个没有路径的 inode 里写;
   在 macOS 上那些输出【再也读不回来】。A 自己则输在端口上,`EADDRINUSE` 退出。
3. A 查端口,看见一个"没人认领"的 smoke 进程占着 3199,判定是上一轮的孤儿,
   `kill` 掉 —— 杀掉的是 B 正在跑的那一次。
4. B 的会话重起一次冒烟。它的 `sweepScratch()` 删掉了 A 此刻正在用的账号。
5. A 那一次死于 `SIGKILL`,`SMOKE_EXIT=137`。

两次互相破坏,**每一次施害方都以为自己在清理一个 stray**,而且按它自己看到的
证据,它的判断是合理的:一个占着端口、不属于任何已知任务的进程,确实
【长得就像】孤儿。这里缺的不是谨慎,是**归属信息** —— 进程和账号都没带上
"我属于谁、我什么时候开始的",于是"活着的别人"和"死掉的自己"无法区分。

**诊断时最容易被骗的一步**:`SMOKE_EXIT=137` 与端口冲突都指向"我的运行失败了",
于是人会去查这一刀改了什么。真正的判据是 `lsof -p <pid> -a -d 1`:
它显示活着的那个进程 fd 1 指向 `/tmp/reach_clean.log` **inode 4733821、3461 字节**,
而同名路径上的文件是【另一个 inode、470 字节】。同名不同 inode = 有人 unlink 过 =
**这棵树上不止一个跑者**。查并发,先查 inode,不要查 diff。

## 要求

- **一棵树,同一时刻只跑一个冒烟。** 不是性能建议,是正确性要求:
  `sweepScratch()` 会删掉另一个跑者的在飞账号,而失败会显示成路由错误。
- **一棵树,一个 Claude Code 会话。** 两个会话跑同一个工作区,共享的不止是
  端口和 `/tmp`,还有 `.next`(`npm run build` 会重写它、搞死正在跑的 dev server)、
  git 索引,以及那个 live 数据库。要并行,就分别开 worktree 加各自的数据库,
  否则就排队。
- **`/tmp` 里的日志按运行取唯一名字**(带 PID 或 HEAD),并且**永远不要
  `rm -f` 一个你不是其作者的日志**。第 2 步那次 unlink 让一整轮十分钟的输出
  再也拿不回来。
- 真要动手杀一个"孤儿"之前,先确认它【真的是】孤儿:`ps -o ppid,lstart`
  看它的父进程与启动时间,`lsof -p <pid> -a -d 1` 看它还在往哪写。
  还在写的东西不是孤儿。

## 又一种并发,而它不在这棵树上 —— **是【库】那一侧被占住了**(PROC-1,2026-08-21)

上面记的都是"同一棵树上两个跑者"。**这一次两个跑者不在同一棵树上,
它们抢的是【线上那个库】。**

**实况:** 冒烟在后台跑着,同时前台单独起了一次 `python3 db/check_mirrors.py`
(为了确认一处镜像漂移修好没有)。冒烟结果:

```
== 186 routes: 174 ok, 3 skipped, 10 FAILED
   FAIL /sales/quotes/[id] → 307
   FAIL /settings/permissions/roles → 307    ← 全部 307,而且全部集中在字典序靠后的路由
```

**十条全是 307(重定向到登录),而且是从某一条开始【一路往后】**——
不是零散的。那是"会话在半路失效了"的形状。

> ### 【机制更正 —— 上面这段原本把病因说错了一层】(SESSION-1,2026-08-23)
>
> **原文是这样写的,一字不改抄在这里:**
>
> > 那是"会话在半路失效了"的形状:页面查权限的那次查询打不通,
> > **`requireModule` 于是把人踢回登录页。**
>
> **`requireModule` 踢不了任何人。** 实测(`app/components/moduleGuard.tsx:52`):
> 它在被拒时**渲染一张说明页**并以 **200** 返回,它没有、也做不到发出一个 307。
> 更要紧的是它压根不会因为"查询打不通"而拒绝 —— `getMyPermissions()`
> (`lib/permissions.ts:45`)在查询失败时**抛错**,那会变成一个 500,不是 307。
> **那十条 307 只可能来自一个地方:中间件**(`proxy.ts` → `lib/supabase/middleware.ts`)。
>
> **真正的机制是 SESSION-1 量出来的那一条:** 中间件当时读的是
> `const { data: { user } } = await getUser()` —— **`error` 被丢掉**,
> 而 `getUser()` 失败时 `user` 也是 `null`。于是【认证够不着】与【这个人没登录】
> 走同一条分支,那条分支就是 `NextResponse.redirect('/login')` = **307**。
> 七种情形的实测表在 `lib/supabase/middleware.ts` 的抬头;其中两行直接对上了当晚:
> **认证一断,连令牌还剩 59 分钟的会话也在 0–3 毫秒内被判成"没登录"。**
>
> **为什么这条更正值得占这么多字:病因错了一层,处置就会找错地方。**
> 按原文的读法,那晚的教训是"别让权限查询超时";按实测的读法,教训是
> **"一个判词说出了它没有确立的原因"** —— 而后者已经由 SESSION-1 修掉了
> (中间件现在把"判断不出"回成 503 并说出来,不再冒充一次登出)。
> 修的地方与原文指的地方**不是同一个文件**。
>
> **上面那段关于 `check_mirrors` 占住连接池的因果【仍然成立】** —— 是它把
> 认证/数据库那一侧压垮的;错的只是"压垮之后是谁把人踢去了登录页"这一句。
> 所以下面那两条要求一个字都不用改。

**原因不在这一刀。** `check_mirrors.py` 会把 ~14,000 行重放推过连接池
(AGENTS.md 那一节写着这正是 OPS-6 把它换成本地重建的理由),而重放期间
那笔事务握着一大批锁。冒烟的每一次页面渲染都要查权限 —— 于是它开始超时。

**独占重跑一次:186 条,184 ok,3 skipped,0 FAILED。** 确认无误。

### 要求(接上面那两条)

- **冒烟跑着的时候,不要单独起 `check_mirrors.py`。** AGENTS.md 已经写着
  "不要单独起一个"(理由是慢),**这里加上第二个理由:它会把并发跑的冒烟
  染成一片假红,而假红看起来和真红一模一样。** 要验镜像就跑 `db/gate.py`
  —— 它做的是【本地重建】,不碰线上那条连接池。
- **而如果已经起了、要停它:用 `pg_terminate_backend`,不要只 `pkill`。**
  这一次实测复现了 AGENTS.md 记的那一幕:`pkill` 之后线上留下一个
  `idle in transaction` 的会话,**10 分 19 秒**,握着它 replay 到一半的锁。
  终止它是安全的(check_mirrors 整支跑在一笔必然回滚的事务里),
  终止后 `mir` schema 0 个、`idle in transaction` 0 条。
