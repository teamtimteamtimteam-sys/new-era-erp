## 一 · 范围:六张表,而不是十五张

**在范围内(六张):** `materials` · `suppliers` · `customers` · `employees` ·
`departments` · `storage_locations`。

它们的共同点是**重建之后是空的**:一个全新的库带不来一行。

### 不在范围内的,每一条都有理由 —— 不是遗漏

| 不做 | 为什么 |
|---|---|
| **五张字典**(`laboratories` / `battery_chemistries` / `substances` / `material_kinds` / `inbound_safety_states`),以及其余每一张 `RUNTIME_CONFIG_TABLES` / `SEED_TABLES` | **它们跟着重建一起来。** `db/check_mirrors.py:94-150` 把它们分成两类:安装种子(`permissions` / `currencies` / `accounts` 的 22 行 `is_system`)与运行时配置(27 张,含全部五张字典)。28 个表镜像里带着种子 `INSERT`。而且它们**已经有一扇编辑的门**(`/settings/dictionaries`,DICT-ADMIN)。**再开一条文件路,是给一张已经有门的表开第二扇门。** |
| `payment_term_templates` · `pricing_formulas` | 各 **1 行**。一个只为一行存在的装载器,是一笔没有付款人的维护成本。 |
| `accounts` | **22 行 `is_system` 是引擎自己的种子**,其余的科目表**按现有种子成立** —— Tim 2026-08-24 裁定:**没有会计师给过一份科目表**。<br>**返回条件:哪天真的有人给出一份科目表,导入它是单独的一刀。** |

## 二 · 测出来的地面

### 2.1 这六张表长什么样(线上实测)

| 表 | 在册行数 | 编号 | 必填且无默认值的列 |
|---|---|---|---|
| `materials` | 9 | 触发器 `MAT-YYYY-nnnn`(**填空式**) | code · name |
| `suppliers` | 4(含软删 12) | 触发器 `SUP-YYYY-nnnn` | code · legal_name · country · counterparty_type |
| `customers` | 3(含软删 6) | 触发器 `CUS-YYYY-nnnn` | code · legal_name · country |
| `employees` | 21 | `next_employee_code`(**MAX(...)+1,不是序列**) | code · legal_name · employment_type · work_category · hire_date |
| `departments` | 1 | **没有取号触发器** | code · name_en · name_zh |
| `storage_locations` | 4 | **没有取号触发器** | code · name |

### 2.2 直插会绕过什么 —— **答案是:什么都不会**

简报最初写的理由是"直插会绕过 RPC 里的拒绝"。**实测之后那句话是假的,所以它没有被写进代码,也不在这里。**

**这六张表【一个建行的 RPC 都没有】。** 它们今天全部由 app 直接 `.insert()` 写入
(各自的 `new/actions.ts`)。守着它们的每一条规矩**本来就是触发器或 CHECK**,
而那两样**任何路径都躲不掉** —— 包括 GO-4 的 `normalise_counterparty_identity`
(登记号去空白 + 大写、空串折成 NULL)。**导入【继承】它们,不复制它们。**

**六张表上一共 11 条 BEFORE INSERT 触发器**,导入一条不落地全都吃到。

### 2.3 那为什么还是走 RPC

**因为事务。** 【N 行的全或全无】+【序列推进】+【写一条日志】必须是**同一笔事务**,
而 PostgREST 一次只发一条语句。这是唯一的理由,也是写在
`master_import_apply` 抬头上的那一条。

## 三 · 定下来的规矩,连同理由

| # | 规矩 | 理由 |
|---|---|---|
| 3.1 | **编号来自文件** | 四支取号触发器都是 `IF NEW.code IS NULL OR = ''` —— **填空式,不覆盖**。所以文件给的编号留得住。它同时是**重跑的识别键**,也让旧系统的编号活下来。 |
| 3.2 | **导入后推进序列** | 见下面单独一节。**这不是家务。** |
| 3.3 | **预览 → 提交,全或全无** | 一张装了一半的表,让操作员**无从判断到底进去了什么**;而下一次重跑就再也分不出"已经导过"与"这是真的第二行"。 |
| 3.4 | **重跑:任一编号已存在 → 拒整份文件并点名** | 跳过会让"已经在了"与"我特意没动它"在屏幕上长得一样;更新是一次**合并**,而合并还没有裁定(`docs/known-issues.md` 的 `COUNTERPARTY-ONE-PARTY` 与那条 post-entry 重复)。 |
| 3.5 | **`tax_id` 只在导入这条路上必填** | 线上 **7 家往来户里 6 家没有登记号**。一条表级 `NOT NULL` 会把那 6 行**就地冻住** —— PROC-1 的 `materials_kind_stated` 正是这样冻住了八行物料,**至今开着**。而一份新导入的批次是有人整理过的数据,那一刻登记号是知道得到的。 |
| 3.6 | **近重复:警告,不拒绝** | 两家真正不同的公司可以同名。比较用的是 `lib/nearDuplicate.ts` —— 系统里**唯一**那份定义(GO-4 建的,三个既有调用点行为未变)。它只返回既有【拼法】,编号在同一份数据里回查,**helper 一个字没改**。 |
| 3.7 | **`departments` 走两遍** | 两条外键都可空,所以两边都做得到。选 departments 是因为**回指只是小表上的一列**(线上 1 行),而两遍走 employees 意味着为了写一个插入时就已经知道的值,回头再过一遍大表。顺序:部门(不带经理)→ 员工(带部门)→ 回填经理。 |
| 3.8 | **导入日志** | 「那个文件到底进去了没有」否则答不了。**它是日志,不是血缘** —— 表注上写着这句,也写着**清库时它跟着一起清**:一条比它的对象活得更久的记录,是本仓库点过很多次名的形状。 |

**`materials` 没有装载顺序约束** —— 它的五个字典外键都是重建时就种好的。

## 四 · 序列推进:为什么它是这一刀最容易被跳过的一步

编号来自文件(3.1),所以**那三条序列一格都没有动**。不推进的话,下一次有人在界面上
新建供应商,取号会从旧位置继续 —— 撞上刚导入的编号,报一句 `duplicate key`,
**而那时没有人会想到是几周前的一次导入造成的。**

**只有三张表需要推进,而"不需要"也是测出来的:**

* `materials` / `suppliers` / `customers` —— 用序列(`material_code_seq` 等)→ **推进**;
* `employees` —— `next_employee_code` 是 `MAX(split_part(code,'-',3)::int)+1`,
  **天然看得见导入进去的最大号** → 不需要;
* `departments` / `storage_locations` —— **根本没有取号触发器**,编号一律由人给 → 不适用。

**证明它的是 `db/fixtures/124`**,而它的判据**不是"序列变大了"** ——
只断言 `last_value` 变了,一个把序列推到某个无关数字的实现也能过。
C 臂走的是**真正的那条路**:插一行 `code` 为空的物料,让触发器取号,
断言它**越过**了刚导入的最大号。

### 四之二 · 一个实测撞出来的上限:**编号只装得下四位**

写那支 fixture 时撞出来的,不是设计时想到的:

```
lpad('9999', 4,'0') = '9999'      lpad('10000',4,'0') = '1000'
```

**PostgreSQL 的 `LPAD` 会截断。** 三支取号函数写的都是
`LPAD(nextval::TEXT, 4, '0')`,所以序列一旦被推过 **9999**,
下一个自动取号就是一个**被静默截短**的编号 —— 第一次可能不撞,第二次必然撞,
而屏幕上是一句 `duplicate key`,没有人会想到是格式截断。

**处置:导入【按名拒绝】超过 9999 的编号(`IMPORT_CODE_NUMBER_TOO_HIGH`),
而不是去推一个会把取号弄坏的序列。** fixture 124 的 H 臂两个方向都钉住
(10000 被拒、9999 放行)。

> **放宽那三支取号函数的位数是【另一刀】** —— 它会改变每一个既有编号的形状,
> 那是一次需要有人拍板的、看得见的改动。本刀只负责**不把系统推进那个状态**。

### 四之三 · 序列推进在【全新重建的库】上根本没有跑 —— fixture 抓住的

**这一条比上面两条都值钱,因为它只在【要紧的那种库】上出现,而且不报任何错。**

`pg_sequences.last_value` 在一条**从来没有被取过号**的序列上是 **NULL**,
而**一个刚重建出来的库正是这种状态 —— 生产就是一次重建**。
第一版的推进写的是:

```sql
IF v_maxnum IS NOT NULL AND v_maxnum > (SELECT last_value FROM pg_sequences …) THEN
```

于是那个比较是 `14001 > NULL` = **NULL**,IF 永不成立,**推进被静默跳过**。
线上跑得好好的 —— 因为线上的序列早就被取过号(76),`last_value` 有值。

> **也就是说:这个缺陷在开发机上永远绿,只在生产那种库上发作,而且不报错。**
> 这正是本仓库反复点名的那一族(`?? []` 把失败读成空集、下游登记的缺席读成事件的缺席)。

**抓住它的是 fixture 124 的 A 臂,而那条臂本来只是一句"前提读得到吗"。**
它在重建库上读到 NULL 就停了 —— **一条前提臂救了它要证明的那件事本身**。
这是 `db/fixtures/README.md` 第 5 条("前提要显式设定")的一个现成注脚:
写前提臂的收益,常常不在它断言的那件事上。

处置:`COALESCE(..., 0)`,写在 `master_import_apply` 里,旁边写着为什么。

> **顺带记一条会咬人的事实:`setval` 不是事务性的,它活过 `ROLLBACK`。**
> 所以 fixture 124 **不要拿去对着线上跑**(它的抬头也写着)。写它的时候我对着线上
> 跑了两次,把 `material_code_seq` 从 76 推到了 14002 —— 那次意外正是上面那个
> 四位截断被发现的原因 —— 随后已还原回 **76**(线上真实最大号 `MAT-2026-0076`)。
> gate 跑在**重建库**上,用完即弃,所以那里是安全的。

## 五 · 文件与模板

* **一张表一个 CSV。** 不是一个文件多个 sheet,也不是一个合并文件 ——
  **按表校验、按表拒绝、按表给模板**,三件事都要求它。
* **模板在【请求时】从 `lib/database.types.ts` 生成**,不是一份手写文件,
  也不在构建时查库。
  * 手写会漂,而没有任何东西会说;
  * 构建时查库意味着**数据库够不着时构建就失败** —— 本仓库一直在拆掉这种形状;
  * `database.types.ts` **是这套 schema 的另一份镜像**,而且 **`db/gate.py` 逐字节
    把它与线上比对** —— 它漂了闸门就红。那正是这条规矩要的保证,零构建期代价。
  * 它在运行时用 `fs` 读一个源文件,所以 **`next.config.ts` 的
    `outputFileTracingIncludes` 里必须有那一行** —— 与发票 PDF 的中文字体同一个坑,
    漏掉它这条路由会**本地全绿、线上炸**。
* **引用按【编号】给,不按 uuid**:`department_code` / `manager_code` /
  `manager_employee_code` / `parent_department_code`。换算在 SQL 那一侧做,
  换不到就是一条**具名**拒绝。一个操作员不可能手打一个 uuid。
* **`status` 不在模板里**:`suppliers.status` 由 `validate_supplier_status_transition`
  管跳转,导入直接落一个状态会绕过那条规矩。
* **`user_id` 不在模板里**:员工 ↔ 登录账号的关联走 `set_user_employee_link`,
  而 LINK-1 那条「两扇门两套规矩」**还没有裁定** —— 这里不开第三扇。
* **CSV 解析用 `papaparse`。** 手写被拒绝的四个理由,每一个都是**静默装错数据**
  而不是崩溃:带逗号或换行的引号字段、双引号转义、Excel(Windows)写的 UTF-8 BOM
  (它会把第一个表头**悄悄**变成认不出来的名字)、以及 CRLF 与 LF。
  `csv-parse` 被否掉是因为它只能在 node 侧跑。

## 六 · 权限

**新的 `action.bulk_import`,只发给 admin。**

**不复用 `action.manage_permissions`** —— 那会重演 DICT-ADMIN 之前的缺陷
(一个物料编辑员永远够不到物料那张屏)。它也**不等于**"能编辑一家供应商":
**它是这一刀里唯一一个一次能放进 500 行错数据的动作。**

导入函数是 `SECURITY DEFINER` + 函数体里 `require_permission`,与本仓库每一支写入
RPC 同形。用 invoker 权限意味着一次 500 行的插入要依赖六张表的 RLS 策略在批量下
表现一致 —— 一个没有收益的新表面。

## 八 · IMPORT-2(2026-08-24):模板发出去的文件,导入现在收得下

**走查的结论是一句话:照着模板填的文件被拒了**,而报出来的是 PostgreSQL 的原话。
走查碰到两列;**实测是六张表、九列** —— 每一张表都有至少一处。

### 8.1 三方对照(模板发什么 / 标什么必填 / 库真正要求与接受什么)

| 表 | ✗ 发了库拒收的列(GENERATED) | ⚠ NOT NULL 但有默认值(空格子被转成 NULL) |
|---|---|---|
| materials | — | `unit` |
| suppliers | **`supplies_goods`** | `supplier_types` |
| customers | — | `credit_hold` |
| departments | — | `is_active` |
| employees | **`monthly_salary_set`** | `employment_status` · `review_exempt` |
| storage_locations | — | `is_active` |

**「必填标记」那一栏一处都没有错** —— 也就是说简报里
「`supplier_types` 是 NOT NULL 却没标必填」的诊断是**反的**:
它 `NOT NULL DEFAULT '{}'`,**不标必填才是对的**。真正的缺陷是导入把空格子
**折成了 NULL**。按原诊断去修(标成必填),会让操作员在每一行手打一个 `{}`
来绕过一个 bug。**一次错误的转换,制造了九处里的七处。**

另外 **六个取值受限的列**此前在任何地方都没有说出它们接受什么:
`suppliers.counterparty_type` · `employees.employment_type` · `.work_category` ·
`.employment_status` · `.residency_status` · `.separation_type`。
其中 `employment_type` 与 `work_category` 是**必填**的 —— 也就是说
今天要导入员工的人**无从知道该填什么**。走查里那三个 counterparty_type 的值
是【口头】补上的,而那正是同一个缺陷在隔壁一列的样子。

### 8.2 模板的来源换了,而理由不是"解析得不好"

`lib/database.types.ts` 里:

```
supplies_goods?: boolean | null    ← 一个 GENERATED 列,与任何普通可选列一模一样
counterparty_type: string          ← 一个 CHECK 闭集,只是 string
```

**那两件事实【不在那份类型里】。** 只有线上目录(`pg_attribute.attgenerated`
+ `pg_constraint`)同时拥有三件事实。所以模板改从
`master_import_template_columns(p_table)` 取。

> **这【不是】推翻「不要在构建时查库」那条裁定。** 那条的理由是
> **库够不着的时候构建就会失败**;而这是**请求时**,并且模板路由本来就为权限
> 判断打了一次往返 —— 没有新增依赖,也没有新增失败模式。
> **理由不适用,不等于裁定被推翻。** 这句话同时写在路由与 `lib/importTables.ts` 里,
> 免得日后有人"恢复"成读类型文件。

### 8.3 写往返测试时撞出来的三件事

**要求是:一份下载下来【一个字没改】就传回去的文件必须走得通。**
一个把自己发出去的文件退回来的系统,正是这一刀在拆的东西。验的时候撞到三处:

1. **papaparse 会【自己猜】分隔符。** employees 的取值说明那一行里有一大把 `|`,
   于是它把 `|` 猜成了分隔符,**整份文件被读错而且不报错**。分隔符现在写死成逗号。
2. **一行的字段比表头多时,papaparse 把多的塞进 `__parsed_extra`,那是一个【数组】**;
   代码里 `.trim()` 会当场抛 TypeError —— 操作员拿到的是一个 500,不是一句话。
3. **一份原样的模板【一定】会带一条 `FieldMismatch`**(说明行只有一个字段)。
   上一版把任何 parse error 都当成致命,于是自己发的模板被自己拒掉。
   现在字段数对不上的那一族交给按行的跳过与校验;**引号没闭合这类仍然是致命的**。

**六张表全部验过:下载 → 原样上传 → 得到「文件里没有数据行」,不是解析错误。**

### 8.4 拒绝按 SQLSTATE 分族

走查见到的两条原文只是两个实例。现在按 **SQLSTATE** 映射八族
(`23502` / `23514` / `23503` / `23505` / `22P02` / `428C9` / `22001` / `22003`),
每一条都带行号与列名。**SQLSTATE 是稳定的,消息文本不是**,而且它覆盖的是一族。
兜底那一条**永远不把 PostgreSQL 的措辞当成我们的话**:它说"第 N 行、列 C 被拒了",
再把原文**引起来**放在后面。

### 8.5 屏幕:选择器画的是【另一个变量】

「上传之后选择器显示物料、而系统处理的是选中的那张表」**不是一个显示 bug**。
`ImportForm` 里有一个 `useState` 的 `table`,而其余每一处读的是 `preview.table`
—— **服务端真正处理的那张表**。两个变量表示同一件事,于是它们可以不一致。
**这已经让一张截图被读错过一次。**
现在只有一个值。顺带:选择器**不再预选**(预选不是选择,而导错表不可撤销),
文件输入在选表之前禁用,并且**长得像一个控件**。
