**How permissions are enforced (Measured):** no action in the slice calls `requireFunction`, `requireEditPermission`, `requireModule` or `can()` before writing. The one exception is `saveCompanyProfile`, which calls `can(DATA_VIEW_BANKING)` only to decide whether the bank columns are included. Method: `grep -nE "require[A-Z]\w*\(|can\(|has_permission"` over the 38 files. Every permission is checked in the database:
- **RPC path:** `require_permission('<code>')` / `has_permission` / `require_approver_for(level)` / `self_leg` inside the function body, extracted from `funcs.csv` (script `at0/fin_rpc.py`).
- **Direct-table path:** RLS write policies (`pg_policies`) plus the statement-level trigger `enforce_write_permission('<code>')` (`pg_get_triggerdef`). Both give the same code for every table listed.
- `require_approver_for(n)` means: the caller holds the role set in `finance_settings.approval_level{n}_role_code` (from `approval_level_eligible`).
- "L2 approver" below is short for `require_approver_for(2)`.

Permission codes in the tables come from these sources. "Measured" means the code was taken from the function body or the policy text.

## 4. Findings

1. **Measured — no server action checks a permission; every check is in the database.** 0 of 88 writing actions call `requireFunction`/`requireEditPermission`/`can()` before writing (the only `can()` is the banking-column filter in `saveCompanyProfile`). The per-operation code shown in §1 comes from `require_permission` in the RPC body, or from the RLS policy plus `enforce_write_permission` trigger args, which were identical for all 17 direct tables (`pg_policies` + `pg_get_triggerdef`, live, postgres/bypassrls).
2. **Measured — the equipment panels on a finance page are gated by processing.** Equipment maintenance, downtime and service intervals (A8, A10–A13) on `/finance/assets/[id]` require `module.processing.edit`, not a finance code. A trail on that page mixes finance and processing operations.
3. **Measured — closing the financial year needs `action.finance_reopen`.** `close_financial_year` requires `action.finance_reopen`, the same code as the reopen actions, not `module.finance.edit`.
4. **Measured — payment requests can be withdrawn by anyone with finance edit.** `withdraw_payment_request` has no `self_leg` (its calls are only `require_permission`), while the other 5 `withdraw_*_request` functions in the slice do call `self_leg`. Any finance editor can withdraw someone else's payment request, so the trail must name the withdrawer and not assume it was the requester.
5. **Measured — three create actions don't know the new record's id.** `createFreightDocument`, `createFxRate` and `openGstPeriod` redirect to the list without the new id. The trail must find those rows by table and key, not from an action return value.
6. **Measured — payment targets are not linked by foreign key.** `payment_requests.allocations` is JSONB (the check constraint shows `jsonb_array_length(allocations)`). Rolling a payment-out request up into the expense, inbound-batch or invoice trail needs a JSON path, not an FK.
7. **Measured — every table the slice writes is captured by `change_log`.** All 71 tables written by the slice (upper bound) have the `zzz_change_log` trigger. `approval_log` is polymorphic (`subject_type`, `subject_id`); the slice uses 7 of the 20 subject types. It holds 15 rows live (count as postgres, bypassrls). `journal_requests` has 0 rows (same query).
8. **Measured — two domain trails already exist on slice pages.** `fixed_asset_history` is shown on `/finance/assets/[id]` by `HistoryPanel.tsx`, and `fx_rate_history` is read on the fx pages. `sales_attribution_log`, `processing_cost_entry_history` and `approval_log` also exist but have no general trail UI in the slice (Inferred from the page `.from()` lists in §3).
9. **Inferred — "all" is an upper bound.** fnmap `all` includes every branch. For example, `submit_*_request` lists payments, journals and so on because it executes immediately when approvals are off. Which tables a single operation actually writes depends on `approvals_enabled` and the request kind.
