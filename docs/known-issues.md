## 验证残留:线上那些 ZZ 行是什么、为什么还在(2026-08-20 记录,LOG-CLEANUP)

物流那一串刀(LOG-1a → CTN-OP)每一次端到端验证都在【线上】造过临时数据。
凡是有门的都按门退了役,**下面这些是退不掉的** —— 列在这里,免得下一个人
把它们读成来历不明的数据,或者更坏:动手去"清理"它们。

### 一 · 退不掉,因为【那扇门不存在】—— 这是两处真的缺口

* **`ports`:12 行 ZZ/Z 开头的临时港口**(ZB6016A/B、ZC7382A/B、ZL4530A/B、
  ZL8817A/B、ZZ2BA/BB、ZZ2LA/LB)。真港口只有 `SG` / `SH` 两行。
* **`lanes`:6 条由那些港口两两组成的临时航段** —— 就是 Tim 在每个下拉里看到的那六条。
  真航段只有 `SG → SH`。

**两张表都有 `deleted_at` 列,每一个读它们的地方也都过滤 `deleted_at is null` ——
而【没有任何一处写它】。** `app/logistics/lanes/actions.ts` 的全部写入路径是:
`addPort` / `addLane` / `addRequirement` / `removeRequirement` / `markLaneReviewed`;
只有 `lane_document_requirements` 有 remove,**港口与航段【建得出来、退不下去】**。

**这不只是清理不掉临时数据的问题**:一个真的港口停用了、一条航段不再走了,
今天同样没有办法把它从下拉里拿走 —— 主数据只能增不能退。
**本刀不补这扇门**(清理不是开新写入路径的时候),按名记在这里。

### 二 · 退不掉,因为【设计上就该留着】

* **`shipments`:`ZZ2B-SHP1` / `ZZ2B-SHP2`** —— 这张表【根本没有 `deleted_at` 列】。
  发货单是发生过的事,不软删。
* **`freight_documents`:`FRT-2027-0001/0002/0003`**(notes 带 `ZZLOG4B`,状态
  `reversed`)。这张表有 `deleted_at`,但**没有软删的门** —— 运费单的"撤销"
  就是冲销(`reverse_freight_document`),而冲销【不抹掉】单据:
  三张都已冲销,分录净额归零,应付账龄里没有它们。留痕本身就是那条设计。
* **`container_milestones`:软删箱子上还挂着 6 条**。只增不改,没有删除的门 ——
  更正的写法是再记一条(LOG-5d),抹掉就等于抹掉更正的历史。
* **用掉的号段**:`CTR-2026-` 到 `0010`、`CTR-2027-` 到 `0006`、`FRT-2027-` 到 `0003`。
  无缝编号意味着**号用掉就是用掉了** —— 空号比重号好,这是那条设计的代价。

### 三 · 已按门退役的(不必再找)

软删完毕:`containers` 里全部 ZZ* 临时箱子(9 个,`soft_delete_container` + 理由)、
`forwarder_rate_quotes` 里全部带 ZZ 备注的临时报价(8 份)、
`suppliers` 里三家临时货代(`ZZ1B-FWD` / `ZZ1C-FWD` / `ZZ2B-FWD`)。

### 四 · 【没有动】的两份在册报价 —— 它们不是临时数据

`forwarder_rate_quotes` 里还有两份在册的、**没有 ZZ 备注**的报价,都挂在 BDP 名下:
`SG → SH` 3,000 USD(`free_days = 7`)与 `ZZ2BA → ZZ2BB` 3,000 USD(未写明)。
认不出是哪一刀留下的,**所以一份都没碰** —— 清理只动认得出来的东西。
(第二份坐在一条临时航段上,那条航段按第一节退不掉;两件事一起看就行。)

## 供应商 status 与下拉:两条【停在这里】的观察(2026-08-20 记录,SWEEP-HYGIENE)

* **线上唯一一家真货代 BDP 至今是 `draft`,而没有任何一条写下来的规则要求
  "开票之前必须先 active"。** FRT-FIX 之后运费录入页照常选得到它(那一页不再过滤
  status),所以这不拦路;要不要走 draft → pending_review → approved → active
  那四步,是一个业务判断,不是一处缺陷。**不动。**

* **全仓没有任何一个供应商下拉过滤 `status`** —— 十一处一律只滤 `deleted_at`
  (加上 counterparty_type 那条轴)。于是 `blacklisted` / `archived` 的往来户在
  每一个下拉里都选得到。**这是一次决定,不是十一处补丁**:要么写下"下拉一律排除
  哪几个状态"并在一处实现,要么明说不管。在有人决定之前,**不动**——
  FRT-1 当年只在运费页单独加过一次 status 过滤,而那一次的下场就是 FRT-FIX。

## 已投用资产的成本【向下修正】没有任何路(2026-08-21 记录,EQP-1b-iii 刻意不建)

**一台已经投用的机器,如果它的成本记多了,今天没有任何机制能把它改小。**
三条路同时是堵死的,而这三条堵死【各自都是对的】:

* **加不了负数**:`fixed_asset_cost_entries.amount_base > 0`,表上的 CHECK;
* **冲不了**:EQP-1b-iii 起,追加笔的冲销在资产已投用时按名拒
  (`ASSET_IN_SERVICE_COST_LOCKED`)—— 折旧已经按那个成本基数算过,其中若干期
  可能已经锁进期间,而这个系统【没有重述机制】;
* **建卡那一笔本来就冲不了**:FIN-22 的 `EXPENSE_HAS_ASSET` 无条件拒绝冲销
  生出资产卡的那笔支出 —— 与投没投用无关。

**顺带记下相邻的那个缺口,免得"冲销现在会退成本"被读成比它更大的一句话:**
一张【完全建错】的资产卡,即便【尚未投用】,也一样退不掉 —— 因为退它要冲销
建卡那一笔,而那一笔恒被 `EXPENSE_HAS_ASSET` 拦着。EQP-1b-iii 修的是【追加】
那一半,不是【建卡】那一半。

**EQP-1c-a 又给这个缺口添了【第三种】形状,一并记在这里:**
`create_fixed_asset` 建出来的【零成本卡】要退场,今天同样没有路 ——
处置按名拒(`ASSET_HAS_NO_COST`:一张没有成本的卡不构成一次处置,而且那条
无条件发出的 1500 贷方会撞上 `journal_lines.amount_ccy > 0`),
而它【连一笔可冲的支出都没有】(`expense_id` 为 NULL)。
业务上它对应的事件是**取消一次采购承诺**,不是【处置一台资产】——
两者在账上完全不是一回事,所以不能靠放宽处置来顺手解决。
线上 `fixed_assets` 今天 0 行,三种形状都还没有绊住过谁。

**还有一条更小的,同源:** 经 `create_fixed_asset` 建的卡,`residual_base` 恒为 0
且此后无法更改(全库只有 `record_expense` 的新建支写过它,而那扇门不走这条路)。
于是这类机器只能按【残值为零】折旧。**刻意不在本刀里开一个设定残值的口子:**
它要么得在成本还是 0 的时候接受一个无从校验的残值(等成本落下来可能已经高过它,
届时是一条裸的 CHECK 违例),要么得单开一条修改资产参数的路 —— 而那条路的形状
取决于第一次真的有人需要它时,他要改的是残值、年限,还是两者。
**返回条件同上:第一次真的发生。**

**为什么现在不建。** 要建的是一条"资产成本调整"的路,而它的形状取决于
**第一次真的发生时那笔钱是什么** —— 供应商退款?计价错误?资本化边界判断
反悔?三者的分录、期间与凭证都不一样,而**照着一个想象出来的案例去设计,
正是这个项目一贯拒绝做的事**(与 `docs/forward-queue.md` 里"现在排它们
就是在猜"同一条)。线上 `fixed_assets` 今天 **0 行**,所以它还没有被谁挡住过。

**返回条件:第一次真的发生。** 那时会有一个具体的金额、一个具体的原因和一张
具体的凭证,而它们正是设计这条路所缺的全部东西。

## `suppliers.supplier_types`:一份【没有规则的清单】,而「没选」与「没人定过」是同一格(2026-08-21 记录,EQP-1c-b 走查带出)

**两件事,同一列,一起记。**

### 一 · 那份清单在数据库那边【什么都不管】

`suppliers.supplier_types` 是 `text[] NOT NULL DEFAULT '{}'`,**没有 CHECK,
也没有对应的查找表**(全库的 RUNTIME CONFIG 查找表只有 `certificate_types`
与 `leave_types` 两张)。四个(EQP-1c-b-fu 之后五个)取值只活在
`app/suppliers/supplierTypes.ts` 这一个 TypeScript 数组里。

**后果:数据库会接受任何字符串。** 直插一个 `ARRAY['banana']` 不会被任何东西拦住。
也就是说这份清单是【建议】,不是【规则】—— 而屏幕上它看起来像后者。

**本刀刻意没有顺手加 CHECK**:线上现存四个取值(dismantler ×1、recycler ×2、
trader ×1,另有 10 家空数组),但「有没有别的写法曾经被写进去过」要先查清楚 ——
而且一旦加了 CHECK,加一种类型就从「改一行 TS」变成「跑一支迁移」,那是一次
**需要有人拍板的取舍**,不是一次顺手。

### 二 · 「一种都不是」与「还没有人填」在屏幕上是同一格

那一列 `NOT NULL DEFAULT '{}'`,所以**「还没有人决定」这个状态根本表示不出来** ——
没有 NULL 可用。表单上这个多选【不是必填】(新建与编辑两条 action 都不校验它),
而列表页渲染的是 `s.supplier_types?.join(', ')` —— 空数组 join 出来是**空字符串**。

于是屏幕上一个空格子同时意味着两件事:
* 这家公司确实【不属于】清单里的任何一种;
* 【还没有人填过】。

**这正是本仓库反复遇到的三态问题**(`lib/permissions.ts` 存在的全部理由就是
「null 本来就有含义」),只是这一次连第三种状态都没有地方放。
线上 14 家里有 **10 家是空数组** —— 这一格现在大部分时候是空的,
而没有人能从屏幕上判断那是哪一种空。

**不在本刀解决,因为它是一次设计决定,不是一次修复:**
要么让那一列可空(NULL = 没人定过,`{}` = 一种都不是),要么在表单上加一个
「以上都不是」的显式选项,要么把它变成必填。**三条路各有代价**,而选哪条
取决于 Tim 要不要把「这家做哪一行」当成一件必须回答的事。

**返回条件:** 主数据查重与约束那一刀(`docs/forward-queue.md` 阶段 3)——
它本来就要面对「切换时录进来的脏主数据」,而这一格正是其中一种。

## 付款触发条件的词汇是【材料形状】的,机器上用不了(2026-08-21 记录,EQP-1c-b 走查,刻意不建)

**走查里一张设备采购单的第三期印着「post assay(化验后)」—— 而一台机器不会被化验。**

**现有的五个触发值**(`purchase_order_payment_terms.trigger_event`,
表单里的 `TRIGGER_OPTIONS`):
`on_order` · `on_shipment` · `on_arrival` · `post_assay` · `fixed_date`。
前三个与最后一个对机器同样成立(下单付定金、发运付、到厂付、定死某一天);
**只有 `post_assay` 是纯材料的** —— 它对应的是"化验出来才知道这批料值多少"。

**机器那一侧真正的等价物,给建它的人:** 一台机器的尾款通常不挂在化验上,
而挂在**它能不能用**上 —— 也就是本模块已经在用的那个铰链:

| 建议值 | 什么时候触发 | 它挂在哪个既有事实上 |
|---|---|---|
| `on_installation` | 安装完成 | 无(要新记一件事) |
| `on_commissioning` | 调试通过 / 验收 | **`fixed_assets.in_service_date`** —— 就是 `set_asset_in_service` 那一刻 |
| `warranty_expiry` | 质保期满(留尾款) | 无(今天全库没有质保期这个概念) |

`on_commissioning` 是三个里唯一【已经有真源】的:投用日是一个已经被记录、
而且只发生一次的事实(EQP-1c-a 的 `ASSET_HAS_NO_COST` 与 EQP-2a 的归属边界
都读它)。

**为什么本刀不建它:** 一台机器的尾款【什么时候该付】是一个**商务条款**,
不是一段代码 —— 它取决于合同怎么谈的:装完付?试车通过付?跑满 30 天付?
留 10% 质保金一年后付?**每一种都对应一个不同的触发值和一套不同的凭证**,
而这四台机器的合同条款没有人告诉过这个系统。
照着一个想象出来的条款去加枚举值,正是这个项目一贯拒绝做的事。
**本刀因此一个已播下的触发值都没有改**(brief 明写)。

**返回条件:第一张真的设备采购单谈定尾款条件的那一天。** 那时会有一份具体的
合同条款,而它正是设计这组枚举所缺的全部东西。

## 抬头地址是【两份各自长出来的副本】,而六个单据里只有两个印它(2026-08-21 记录,EQP-1c-b-fu2)

修「新加坡印两遍」时数出来的两件事,都不是那个 bug 本身:

**一 · 公司抬头没有共用的版式,只有两份副本。**
全库只有两处渲染 `company_profile`,而且拼法不同:
* 采购单:`[address_lines, city, postal_code, country].join(', ')` —— 一行逗号;
* 发票:城市行 `[city, postal_code].join(' ')`,之后【另起一行】印 country。
本刀抽出来的是**那条判断**(`lib/companyAddress.ts` 的 `countryIfDistinct`),
**不是整块抬头** —— 两边的版式是刻意不同的,统一它会改掉发票的样子。
一条规则一个实现,版式一个像素没动。**但"两份副本"这件事本身留在这里**:
下一次要改抬头(加税号?加 GST 号?)的人,要改两个地方,而没有任何东西会提醒他。

**二 · 六个对外单据里,只有两个印我们自己的地址。**
实测 `company.*` 的引用数:采购单 7、发票 21、**报价单 0、送货单 0、
贷项凭证 0、销售订单 0**。也就是说客户手里的报价单与送货单上【没有我们的地址】。
这可能是刻意的(送货单随货走,地址在运单上),也可能是四份文档各自漏了 ——
**本刀没有查证是哪一种,所以只报数字,不下结论。**

**返回条件:** 对外单据版式那一刀(`docs/forward-queue.md` 阶段 8 的「对外单据版式」)
—— 它本来就要把这几份文档摆在一起看。

## 改单历史说「表头变了」,但不说【什么】变了(2026-08-21 记录,EQP-1c-b 走查,先于本模块)

采购单详情页的改单历史渲染 `change_type`(例如 `header`),于是屏幕上是一句
「表头变了」—— 而**这个仓库在同一张表里就存着答案**:`purchase_order_history`
带着成对的强类型旧/新列(`old_order_date`/`new_order_date`、
`old_estimated_total_ccy`/`new_estimated_total_ccy`、`old_incoterm`/`new_incoterm` …
共十一对),外加 `amend_reason`。

**也就是说数据早就够了,是渲染没有用它。** 一句「表头变了」在审计面前等于没有
记录:它答不出"是谁把交期从 3 月挪到 5 月的"。

**先于本模块,也不是本模块造成的** —— 采购单改单是 PUR-2 的东西。记在这里是因为
走查看到了它,而看到了不记下来,下一次还得重新发现一遍。

**返回条件:** 采购单界面下一次被打开时;或者第一次有人问"这张单到底改了什么"。

## app/ 里【直接查遮蔽表】的地方有三十来处,它们今天不炸靠的是运气(2026-08-21 记录,EQP-1c-c-fu 普查;先于本模块)

**背景:一次真实的线上故障。** EQP-1c-c 给开支表单加的采购行下拉查了
`purchase_order_lines`(表),而它是遮蔽表 —— `REVOKE SELECT` + 列清单授权 ——
且该下拉要的 `estimated_amount_ccy` 正是被扣住的三列之一。页面对每一个登录用户
都是 `42501`。**闸门全绿、冒烟 0 FAILED,是人用手点出来的。**

**普查的结果:全库 24 张遮蔽表,而 app/ 里【直接查表】的地方约 30 处。**
它们今天大多不炸,原因只有一个:**那几条查询碰巧只点了【已授权】的列。**
列清单授权是【按列】的,所以"查表"本身不违法 —— 违法的是点到被扣住的那几列。
于是判据变成了"我这次只选了安全的列",而那不是一条判据,那是一次运气:
**哪天有人往 select 里加一列,页面就会在那一刻 42501,而没有任何一道闸看得见。**

**本刀只修了设备那几刀自己引进的**(见提交信息里那张逐条表),
**其余的一概只报不修** —— 它们先于本模块,而一次性改三十处查询是一次
独立的、需要自己走查的刀。

**⚠️ 那条 PostgreSQL 的提示不能听。** 报错会建议
`GRANT SELECT ON purchase_order_lines TO authenticated`。照做会把遮蔽整个撤掉,
把金额列敞给每一个登录用户。**提示是机械的:它不知道那几列是故意扣住的。**
正确的修法永远是【改读 `<表>_masked` 视图】。

## 提议(未建):一个能查出"直接查遮蔽表"的检查(2026-08-21 记录,EQP-1c-c-fu)

**它该住哪:** `scripts/check-masked-reads.mjs`,与 `check-currency-literals.mjs`、
`check-error-swallowing.mjs` 同一族 —— 进 `npm run build`(快反馈)与
`db/gate.py`(拦得住),带一个写明理由的 ALLOWLIST。

**它要做什么:** 扫 `app/**/*.ts(x)` 里的 `.from('<t>')`,当 `<t>` 存在
`<t>_masked` 伴生视图时报出来。真源是【目录】(`pg_class` 里那 24 张视图),
不是一份写死的清单 —— 加一张遮蔽表,这道检查自动跟着变宽。

**它要花什么:** 一次正则扫描,毫秒级;真源那一半要一次目录查询(gate 里本来
就有连接)。**便宜到可以每次跑。**

**⚠️ 它【看不见】什么 —— 这一段比上面三段都重要,因为本仓库最反复的失败
就是"一个覆盖面窄于它名字的检查"**(`--reach` 对动态路由、`check-error-swallowing`
对 `if (error) return []`、`colgrant` 对"谁在读"):

1. **它分不清【嵌入名】与【列名】。** PostgREST 的 `select('a, b, rel(x)')` 里
   `rel` 是一个关系嵌入,不是列。**本刀写那个一次性扫描器时就踩了这个** ——
   它把 8 处嵌入名报成"点了被扣住的列",而其中至少一处(`expenses/[id]`)
   经实测是通得过的。要真的判"这条查询会不会 42501",得解析 PostgREST 的

2. **它看不见拼出来的表名**(`.from(someVar)`)。
3. **它看不见 RPC 里的读**(DEFINER 函数以属主身份跑,本来就不受这条约束,

## 货代的【非运费】收费今天没有门(2026-08-20 记录,LOG-4b 查证)

**现象**:`/finance/expenses/new` 的往来对象下拉排除货代
(`app/finance/expenses/new/page.tsx:37`,LOG-1b 加的
`.neq('counterparty_type', 'forwarder')`)。于是一笔【不是运费】的货代收费
(年度账户费、EDI 订阅、与任何一票货都无关的杂费)在这套系统里没有任何入口:

**为什么这条排除【仍然是对的】,不是要修的东西**:货代的收费有自己的单据类型,
而 LOG-4a 之后它覆盖【两个方向】。允许同一个对手方走 `record_expense`,等于给
同一笔负债开第二扇门 —— 那笔钱会以 `doc_kind='expense'` 出现在账龄里而不是
`'freight'`,箱子的运费面板看不见它,实际 vs 报价的比较也漏掉它,而且它绕过
方向、箱子引用与分摊守卫。**两个下拉是互补的**:运费表单
`.eq('counterparty_type','forwarder')`,开支表单 `.neq(...)`,恰好把平面分成两半。

**与 SUP-TYPE-1b 那条规矩不冲突 —— 两者管的是【不同的轴】**:那条规矩说的是
`supplies_goods`(会不会供货)为假的往来户必须留在开支/付款/运费/加工成本四个
下拉里。开支表单【不按 supplies_goods 过滤】,所以房东、水电这类
`service_vendor` 原样在册,规矩照旧成立。货代排除走的是 `counterparty_type`,
是 LOG-1b 另加的一条轴。

**与 PAY-FRT 在 `/finance/payments/new` 上删掉同一句话也不冲突**:付款没有
"第二扇门"可言 —— 不让选货代,未付运费就【永远付不掉】。那里删是对的,
这里留也是对的,理由不同而结论各自成立。

**暂不修的代价**:上面那类非运费收费只能走人工分录,或者被硬塞成一张运费单。
要修的话,正确的形状多半是给 `record_expense` 开一条"这一笔不是运费"的显式路径,
而不是把排除条件直接删掉 —— 删掉就等于把第二扇门重新打开。

## 月初凌晨的服务端分录日期与期间锁(2026-08-06 记录,FIN-20 后基本消除)

  可见的导航项仍然由 `getVisibleModules()`(即 `lib/modules.ts` + 权限)决定,
  那一段一个字没动。
* **登录页是公开路径**,可达性本来就不由角色决定。

**换句话说:`--reach` 断言的是"这个角色够不够得到这一页",而本刀改的是
"够不到的时候屏幕上说什么"。** 两者不相交。

**它欠的是别的东西,而那笔债记在别处:** `docs/manual-walk-list.md` §14 ——
认证这条路上几乎每一件事都只有人眼看得见,`--reach` 与冒烟都够不到。

**现存的 `--reach` 欠账不受本刀影响,原样还欠**(四条静态路由 + DICT-ADMIN 的
`/settings/dictionaries`),见本文件上面那几条。

## CODE-WIDTH-4 · 三支取号函数的编号【只装得下四位】,越过就静默截短(IMPORT-1 实测,2026-08-24)

**`generate_material_code` / `generate_supplier_code` / `generate_customer_code` 都写着
`LPAD(nextval(...)::TEXT, 4, '0')`,而 PostgreSQL 的 `LPAD` **会截断**:**

```
lpad('9999', 4,'0') = '9999'      ← 好的
lpad('10000',4,'0') = '1000'      ← **被截短**
lpad('14002',4,'0') = '1400'
```

**后果:序列一旦被推过 9999,下一个自动取号就是一个被截短的编号。**
第一次可能侥幸不撞,**第二次必然撞** —— 而屏幕上是一句
`duplicate key value violates unique constraint "materials_code_key"`,
**没有任何人会想到是编号格式截断造成的。**

### 它今天有多远

线上三条序列实测:`material_code_seq` **76** · `supplier_code_seq` **426** ·
`customer_code_seq` **122**。离 9999 都还很远,**所以它今天不是一个正在出错的缺陷**。

### 为什么现在记它

**IMPORT-1 的序列推进让它第一次【够得到】** —— 一份带着高位编号的导入文件
(旧系统的编号常常是五位)会把序列直接推过去。**IMPORT-1 因此按名拒绝
超过 9999 的编号**(`IMPORT_CODE_NUMBER_TOO_HIGH`,fixture 124 的 H 臂两个方向都钉住),
而**没有**去改这三支函数。

### 删除条件

把编号位数放宽(例如 `LPAD(..., 5, '0')` 或改成不补零)。
**那是一次看得见的、需要有人拍板的改动** —— 它改变**每一个新编号的形状**,
而既有编号仍是四位,于是同一张表上会并存两种宽度。
真正要决定的是"要不要让新旧编号看起来不一样",那不是一次顺手。

**返回条件:任一条序列接近 9000,或者第一次真的要导入五位编号的历史数据。**

## AUTH-BLAST-RADIUS · 认证一断,**所有人立刻同时掉线**,与令牌还剩多久无关(SESSION-1c,2026-08-23 实测)

**这一条不是上面那条修复的脚注,它是一个独立的、量出来的事实。** SESSION-1c 改掉的是
【症状怎么说】;**依赖本身一个字没变:GoTrue 停,整个系统停。**

`lib/supabase/middleware.ts` 里那个会让人动手的地方。

**三 · SESSION-1c 改了症状,没有改依赖。** 今天:503 + 一句"判断不出",路径保住。
此前:静默重定向到一张什么都不说的登录表单,打过的字全丢。
**后者严格更坏,但两者都是"系统停了"。** 真要让它不停,是 `AUTH-FAIL-OPEN` 那一条。

### 删除条件

`AUTH-FAIL-OPEN` 落地(那时认证短暂不可用不再让全站停摆),或者有人决定这个
依赖是可以接受的并写下理由。**不要因为症状变好看了就删掉本条。**


## AUTH-ERROR-SWALLOWED · 49 处 `getUser()` 仍然丢掉 `error`(SESSION-1c,2026-08-23 在册)

`scripts/check-auth-error-swallowing.mjs` 落地时的在册清单,基线在

## AUTH-FAIL-OPEN · 让认证短暂不可用时系统【继续能用】,而它缺的是一次测量(SESSION-1c 排期,2026-08-23)

**SESSION-1c 选择了 fail closed:判断不出就挡住并说出来。** 代价照直写:
**一次短暂的认证故障从此更显眼,而不是更轻。** 它仍然严格好过此前(静默把所有人
扔到登录页并毁掉他们打的字),但它没有让系统在认证抖动时继续可用。

### 放行(fail open)的论据是真的

**中间件不是安全边界。** JWT 由 Postgres 自己验签验期(RLS 与
`has_permission()` 都建立在它上面),所以**一个混过中间件的伪造令牌,到了库那一侧
照样被拒** —— 攻击者拿到的是一个空壳子,不是数据。这与 `moduleGuard.tsx:18`
写着的那句"这不是安全边界,边界在数据库"是同一条。

### 它为什么是单独一刀:**有一件事没有人量过**

> **有没有哪个页面【直接拿令牌自己的 claim】去渲染 —— 名字、角色、id ——
> 而不读一次数据库?**
>
> * 一处都没有 → 放行在效果上是安全的,而且是一次真的可用性收益;
> * 有 → **那些就是真正的风险面**,必须先点名,再决定放行时它们怎么办。

**本刀做过一次【预备】测量,它不是答案:** `app/` 的 .tsx 里读
`user.email / user_metadata / app_metadata / phone` 的共 **3 处** ——
`app/components/TopNav.tsx:81`、`app/welcome/page.tsx:20`、`app/set-password/page.tsx:29`,
三处都只渲染邮箱。**这不足以下结论**:它没有查 `user.id` 被用作查询参数
(那是读库,不算)与被直接渲染(那算)的区别,也没有查 Route Handler 与动作。
**那次普查是那一刀的第一步,不是本条已经替它做完了。**

### 返回条件

上面那个问题被真的量过之后。**不要在量它之前动手** —— 一次放行如果建立在
"应该没有页面这么写吧"上面,那正是这个仓库反复付账的那种检查。


## AUTH-NULL-AUTHOR · 一次瞬时认证故障会静默记下一行【没有作者】的数据(SESSION-1c 报告,2026-08-23,未修)

`AUTH-ERROR-SWALLOWED` 里最大的那一类:服务端动作写
`created_by: user?.id ?? null`。`getUser()` 瞬时失败时 `user` 是 undefined,
于是那一行**带着 NULL 作者写进去,而且什么都不会报错** ——
实测 `public` 里 `created_by` / `updated_by` **没有一列是 NOT NULL**(0 列)。

**这是【受限不是零】那条病,长在审计线索上:**「我们说不出是谁干的」与
「没有人干」记成了同一个值。

### 已经发生过吗 —— 查过了,答案是【没有证据说发生过】

线上 7 张表抽查,13 行 NULL 作者,**每一行都有一个无辜的解释**:

* 11 行带 `ZZ-` 临时码(`ZZ-SMOKE-*` / `ZZ-STK1CONF-M` / `ZZ-IODCONF-M` /
  `ZZ-1BCONF-M` / `ZZ2B-C1` / `ZZ2B-C2`)—— 冒烟与走查的残骸,那些路径本来就没有会话;
* 余下 2 行 `OUT-2026-0003` / `OUT-2026-0004` 的 `created_at`
  **精确到微秒完全相同**(`2026-06-10 20:18:31.400423+08`)—— 那是一次批量插入,
  不是两次人的动作。

> **说法必须准:这是「没有哪一行缺少无辜的解释」,不是「它可证明从未发生过」。**
> 一次瞬时故障留下的 NULL 与上面这些**长得一模一样**,而这个区别正是本条
> 【留在队列里而不是被当成事故】的全部理由。

### 修它要先裁一件事

判断不出作者时,应当**拒绝这次写入**,还是**记一个与 NULL 不同的「未知」**?
后者是 schema 改动(那一列现在可空,而可空已经另有含义)。**两条路的代价不一样,
而没有人被这件事绊住过** —— 所以它排队,不抢在 `AUTH-ERROR-SWALLOWED` 前面。

### 返回条件

那 49 处被逐条判的时候(它们是同一批代码),或者第一次真的出现一行说不清作者的数据。

## `inbound_batches.status` / `output_batches.status`:没人写、没约束、却在界面上(STK-1 记,2026-08-12,未修)

两张批次表各有一列 `status text NOT NULL DEFAULT 'draft'`:

* **没有 CHECK** —— 取值不受任何约束;
* **全库没有任何写入者** —— 逐条查过 `db/functions/` 里每一处
  `UPDATE inbound_batches` / `UPDATE output_batches`,以及每一处 `SET status =`;
  唯一靠近批次表的 `status = 'reversed'` 是 `rollback_processing_run` 写在
  **processing_runs** 上的,不是批次;应用侧的 action 也一律不传它;
* **线上 16 / 17 行一律是 `'draft'`**;
* **然而它在屏幕上** —— `app/inbound/page.tsx` 的列表渲染 `{b.status}`,
  CSV 导出也带着它。

于是它是一个**永远显示 "draft" 的列**,而读的人无从知道那是"这批货还是草稿"
还是"这一列根本没人维护"。这正是这个仓库反复付账的那种形状:一个看起来在
表达什么、实际什么也没表达的字段,比没有这个字段更坏。

**STK-1 为什么绕开它而不是接管它**:库存状态(可用/暂扣)与这一列毫无关系,
但**名字已经被占了**。在同一批表上让 `status` 同时表示两件事,是下一个人必然
读错的设计 —— 所以新列叫 `stock_status`,而这两列**一个字都没碰**。

**退役它是一次独立的小刀**,而且不是"删掉就行":要先决定
(a) 界面那两处显示怎么办(直接去掉,还是换成真正有意义的 `stage` / `state`),
(b) CSV 导出的列要不要保留(有人可能已经在下游按列位取数),
(c) 删列还是留列加注释。三个都是判断,不该混在一次别的刀里顺手做掉。

## 收货库位【录不进去】—— ctx 机制到不了 PostgREST 的插入(IOD-1 报告,2026-08-12,未做)

IOD-1 的设计里,三个建批次的表单应当把一个【可选库位】经既有的 ctx 机制
传给收货触发器。**做不到,而原因是结构性的,不是写法问题。**

那个"既有机制"是 `commit_processing_run` 在用的
`set_config('evoltrya.movement_ctx', …, true)` + 触发器 `current_setting(…)`。
它成立的前提是**设置与插入在同一个数据库会话、同一个事务里** —— 而
commit_processing_run 整个就是一个数据库函数,所以天然满足。

三个建批次的地方不是数据库函数,是 app 里的 PostgREST 插入
(`supabase.from('inbound_batches').insert(...)`)。它们:

* 每一次调用都是一个【独立的 HTTP 请求】,因而是独立的会话与事务 ——
  `is_local => true` 的 GUC 在上一个请求结束时就没了;
* 而且 `set_config` 根本不在可调用的范围里:它住在 `pg_catalog`,PostgREST
  只暴露 `public`。实测:`POST /rest/v1/rpc/set_config` → `404 PGRST202`。

**所以 IOD-1 只落地了触发器那一侧**:`emit_batch_receipt_movement` 会读
`evoltrya.location_ctx`,不为空就把库位写进收货流水。今天没有任何调用方设置它,
所以每一次收货仍然落在【未指定库位】—— 那是一个合法状态(转移随时可以指定),
但**表单上没有库位这一栏**,与 IOD-1 的意图不符。

### 要做成,需要先决定用哪条路(三条,都不是小改)

1. **把三个插入改成数据库函数**(`receive_inbound_batch(...)` 之类):库位成为
   函数参数,函数内部 set_config 再插入,一个事务。最贴合既有机制,但等于
   给三条创建路径各写一个 RPC,并把三处表单改成调它 —— 是一次独立的刀。
2. **批次表加一列 `location_id`**,触发器读 `NEW.location_id`。最省事,但它与
   STK-1 定下的形状冲突:一个批次可以同时散在几个库位,批次上放一个库位
   会立刻自相矛盾(而且那一列在第一次转移之后就是错的)。
3. **收货后自动补一次转移**:插入照旧落 NULL 桶,紧接着调
   `create_stock_transfer` 把它搬到选中的库位。今天就能做,不动 schema ——
   代价是台账上每一次带库位的收货都会多出一对转移行,而那两行记录的是
   "系统替你做的一次搬运",不是真的搬过。要不要接受这个代价是 Tim 的判断。

**在选定之前,`evoltrya.location_ctx` 这条读取路径是【暂时无人调用】的** ——
留着是因为路线 1 一旦选中它就直接可用;记在这里,免得下一个人以为它坏了。

## `sales_records.movement_id` 只记一次销售的【第一条】流水腿(IOD-1 记,2026-08-13,未修)

IOD-1 之后,一次销售会按库位桶【逐桶写一行】流水(drain_stock)。而
`sales_records.movement_id` 是一个单值外键 —— 一次销售现在可能对应 2、3 行,
那一列只存得下第一行。

**今天为什么不痛**:线上所有流水的库位都是 NULL(库位这个轴 LOC-1 才落地),
所以每一次销售都只跨一个桶、只写一行,`movement_id` 与它一一对应。
**第一次有人把一批货分放两个库位再整批卖掉,这一列就开始只讲一半的故事。**

**它今天被谁读**:没有生产代码按 `movement_id` 反查流水(销售页读的是
sales_records 自己)。所以这是一处【将来会误导人】的字段,不是一处正在出错的字段 ——
记在这里,而不是等某天有人拿它做对账、发现数量对不上再回头查。

**修法是一张腿表,而那是它自己的一刀**:`sales_record_movements(sale_id,
movement_id)`,一次销售 N 行。要一并决定的两件事:

而会撞上它的人是【读 sales_records 的人】,不是读那个函数的人。写在这里,
是让它出现在会去找它的那条路上。

## 盘点看不见【桶】:差异一律落在 available,而 state 不重算(SO-2 记,2026-08-14,未修)

**两条,同一处代码,分开写是因为修法不同。**

`post_stocktake` 对每一条有差异的盘点行做两件事:

```sql
INSERT INTO inventory_movements (..., movement_type, qty_delta, ...)   -- 【不给 stock_status】
VALUES (..., 'adjustment', v_delta, ...);
UPDATE output_batches SET remaining_qty = v_line.counted_qty ...       -- 【不重算 state】
```

**① 差异一律落进 `available` 桶** —— 因为那一行不写 `stock_status`,吃的是列默认值。
盘点数的是**物理总量**(`remaining_qty`),而库存现在分三个桶:可用 / 暂扣 / 已承诺。
于是一次盘亏会把整个差异从可用里扣掉,哪怕短少的其实是被扣住或已许出去的那部分。
盘亏够大时,`check_no_negative_bucket` 会在提交时拒掉整张盘点单,报的是
`STK_NEGATIVE_BUCKET` —— **一条正确但读不懂的拒绝**:盘点的人没做错任何事。

**这不是 SO-2 引进的**:`on_hold` 从 STK-1 起就有同样的问题。但暂扣是罕见且刻意的
动作,而预留是日常动作,所以它从一个理论缺陷变成了一件会发生的事。**记在这里而不是
顺手修掉**,是因为正确的答案是一个**业务判断**,不是一次实现选择:

* 盘点点的是物理总量,还是"我能看见的可用货"?
* 差异该落在哪个桶?按现有三桶的比例摊?全落 available(今天的行为)?还是让盘点
  的人**逐桶点数**(那意味着 `stocktake_lines` 要多一根状态轴)?

三个答案对操作流程的要求完全不同。在预留这一刀里替人选一个,正是这个仓库反复付账的
那种事。**修法草案**:`stocktake_lines` 加 `stock_status`(默认 `available`),点数按桶;
过渡期内,盘亏超过 available 时按名拒绝并**说清楚是哪个桶挡住的**(而不是抛
`STK_NEGATIVE_BUCKET`)。

**② `state` 不重算。** `record_output_sale` 是 `output_batches.state` 的**唯一** UPDATE
写入者(它按 `remaining_qty` 归零与否写「已售罄」/「部分售出」)。`post_stocktake` 把
`remaining_qty` 直接设成盘点数却不碰 `state`,于是**一批被盘成 0 的货仍然显示「部分售出」**,
而一批盘盈回来的「已售罄」批次也不会变回去。今天线上没有已过账的差异行,所以还没有
人看见过。修法是把那个 CASE 抽成一个函数,两个写入者共用 —— 但**不要在这一刀里加第二个
state 写入者**:SO-2 的一条明确决定就是预留不碰 `state`,而"谁写这一列"必须保持
只有一处可数。

### 原因定位了,而此前那句"网络劣化"说得太宽(NET-CHECK,2026-08-16)

一整天的报告都写着"网络劣化"。**那句话说得太宽:Tim 自己的访问一直正常。**

## 员工 ↔ 登录账号的关联:【两扇门,两套规矩】(LINK-1,2026-08-19,未修 —— 要先裁定,不是先写守卫)

LINK-1 给员工表单补了一栏「登录账号」(`app/hr/employees/EmployeeForm.tsx`,
身份组)。补之前这一栏只有账号那一头有;补之后,**同一个事实(`employees.user_id`)
有了两个写入入口,而它们此刻遵守的不是同一套规矩。** 这一条记的就是那个不一致。

### 1 · `set_user_employee_link` 对「账号已经绑在别人身上」**不拒绝,是改绑**

函数体里先跑这一句:

```sql
UPDATE employees SET user_id = NULL
WHERE user_id = p_user_id AND (p_employee_id IS NULL OR id <> p_employee_id);
```

**旧员工那一行的 `user_id` 被【先清掉】,所以 `employees.user_id` 上的 partial
unique index 一次也不会响。** 唯一性约束在这条路上【根本不参与】—— 它拦得住两行
同时持有一个账号,而这里从来不会出现那一瞬间。

因此员工表单那一侧的拒绝(「该账号已关联到另一名员工(EMP-xxxx)」)
**是应用层自己查一次、自己拒的**,数据库不在后面兜底。**它是 TOCTOU 的**:
查与写之间另一个会话把那个账号绑走,第二次写照样成功,而且是静默改绑。
并发下不可靠,单人操作下够用 —— 现状是后者,所以暂不修。

### 2 · 【两扇门带着不同的规矩】—— 而这才是真正要修的东西

| 门 | 文件 | 选中一个【已被占用】的对象时 |
|---|---|---|
| 账号侧(旧) | `app/settings/permissions/UserRow.tsx` | **静默改绑**:把账号从旧员工手里拿过来 |
| 员工侧(新) | `app/hr/employees/EmployeeForm.tsx` | **拒绝**,并说出占用者的工号 |

两侧调的是**同一个函数**,行为的差别整个来自应用层。账号页那一头的语义是
"这个账号归谁" —— 改绑正是它要做的事;员工页这一头的语义是"这个人用哪个账号" ——
把别人的账号悄悄夺过来是一次事故。**两种读法各自成立,这正是麻烦所在。**

> **要修它,第一步不是写一条守卫,而是【裁定哪一侧的语义是对的】。**
> 先决定"选中一个已被占用的账号"到底应该是改绑还是拒绝(还是"要确认的改绑"),
> 然后让**两扇门和那个函数**一起服从那个裁定。在裁定之前写守卫,只会把不一致
> 从两处变成三处 —— 本仓库对"一个事实两处陈述必然漂移"已经点过很多次名,
> 这里是它的一个变体:**一个事实两处陈述,而且两处说的还不一样。**

### 3 · A 换成 B 要保存两次

函数另一头的守卫(`v_owner IS NOT NULL AND v_owner <> p_user_id` →
`EMPLOYEE_ALREADY_LINKED`)在【这名员工已经持有另一个账号】时触发,所以
**从账号 A 直接改到账号 B 会被拒**。要先把这一栏改成「未关联账号」保存一次,
再关联 B —— 两次保存。员工表单为此单出一句话(`hr.errEmployeeHasAccount`),
因为函数抛出来的那个工号是【正在编辑的这名员工自己】,照抄账号页那句会变成绕口令。

### 4 · 字段更新与关联是两次写入,不在同一个事务里

`updateEmployee` 先调 `set_user_employee_link`(好让它的拒绝落在任何字段被改之前),
再 `UPDATE employees`。**两次写各自成败**:关联改成了而随后字段更新失败,
一次保存就落成了两个结果里的一个。要让它们同生共死,需要一个把两件事装在一起的
库端函数 —— 那是库改,LINK-1 是一刀只动渲染层的活,所以记在这里。

### 删除条件

**上线时那一刀【把真实组织架构录进去】的切次。** 那一刀必然要成批建员工、
成批发账号、成批关联,是"两扇门到底哪一侧对"这个裁定**非做不可**的时刻,
也是它唯一值得做的时刻。裁定落地、两扇门与函数对齐之后,删掉本条。

## 保养间隔的粒度只到 `kind`,而"换油 / 换皮带"配不出来(EQP-2c,2026-08-21,未修 —— 要先改 2b 的表)

`equipment_service_intervals` 的唯一键是 **`(equipment_id, kind)`**,而 `kind` 的域只有
两个值(`'service'` / `'repair'`)。也就是说,**一台机器最多只能配出两条间隔**,
而现实里的保养计划通常是好几条并行的:换油每 5 万公斤、换皮带每 20 万公斤、
年检每 365 天。**今天这三条只能压成一条。**

**这不是一次偷懒,是被排期逼出来的,而且另一条路【看起来能走、其实是死的】。**
到期的推导要算"距上一次【那一种】保养",所以间隔与保养记录必须按同一个维度对得上。
今天库里能表达"那一种"的**只有** `equipment_maintenance.kind` 这一列 ——
而那是 EQP-2b 的表,EQP-2c 的 brief 明写着不碰。于是:

> **若给间隔表单独立一套 `service_type`(换油 / 换皮带 …),它将【永远匹配不到任何
> 一行保养记录】** —— 因为 `equipment_maintenance` 上没有这一列。
> 每一条这样的间隔都会永远读成"从未保养过",基线永远停在取得日,
> 而 `is_due` 会随时间必然变成 true 并且**再也灭不掉**。
> **一个永远停在基线上的推导比没有更坏,因为它看起来在工作** ——
> 与 SUP-TYPE-0 那盏"永远亮着、房东不会去办危废证"的灯是同一种病。

所以本刀选择了【表达得少,但每一条都算得准】,并把这一条记在这里。

**当前的绕法(可用,但要知道它是绕法):** 把"这台机器的保养"当成一条合并的间隔,
按最短的那个周期配;`notes` 里写清它其实合并了哪几项。
**代价是显式的**:换皮带会跟着换油的节奏一起报,而系统分不出来。

### 删除条件

1. `equipment_maintenance` 加一列 `service_type`(**这是主刀** —— 它决定域住在哪里:
   一张目录表,还是一条 CHECK。倾向目录表,与 `certificate_types` 同形,因为
   "有哪几种保养"是操作员会改的东西);
2. `equipment_service_intervals` 的唯一键从 `(equipment_id, kind)` 扩成
   `(equipment_id, kind, service_type)`;
3. `equipment_service_status` 里那句 `em.kind = i.kind` 跟着扩成两列相等 ——
   **推导本身一个字都不用改**,这正是当初把 `kind` 留在键里而不是只按机器一行的理由;
4. fixture 111 加一臂:同一台机器上两条不同 `service_type` 的间隔,

**这一条与本文件里 EQP-2b 那条「大修资本化今天走不通」是同一族**:
两条都是"设备模块的下一刀要动 2b 的表",可以合并成一刀,也可以不合。

## 设备三张表【没有 RPC】,于是它们的拒绝是【约束违反】而不是具名业务码(EQP-2d,2026-08-21,已缓解未消除)

`equipment_maintenance`(EQP-2b)、`equipment_downtime`(EQP-2a)、
`equipment_service_intervals`(EQP-2c)三张表**一个 RPC 都没有** ——
写入走 PostgREST 直连 + RLS。于是它们的每一条拒绝到达浏览器时长这样:

```
new row for relation "equipment_service_intervals" violates check
constraint "equipment_service_intervals_at_least_one"
duplicate key value violates unique constraint "uq_equipment_downtime_open"
```

**本仓库其余每一支 `*ErrorCodes.ts` 解析的都是 `CODE|参数` 形状的具名码**,
对着上面这种消息只会原样吐回去 —— 也就是把 Postgres 的英文机器话打到操作员脸上。

**EQP-2d 的缓解:** `app/finance/assets/equipmentErrorCodes.ts` 按【约束名】认,
把全部 **16 条**约束接上了 en/zh 两句人话,并且 `check-i18n` 的
`equipment.errors.*` 后缀集合**现读那个 Set** —— 加一条约束而不写句子,
`npm run build` 当场红。**所以今天屏幕上不会出现裸约束名。**

**为什么这只是缓解,不是消除 —— 两条,都写清楚:**

1. **约束名是【实现细节】,而现在它成了一份对外契约的一半。** 有人重命名一条
   约束(一次纯粹的整理),句子就静默失配,消息退回裸英文,而**没有任何检查会红**
   —— `check-i18n` 只保证"Set 里的每个名字都有句子",不保证"每条约束都在 Set 里"。
   具名业务码没有这个毛病:改了码名,抛它的那个函数就在旁边。
2. **`NOT NULL` 违反根本没有名字可认**(消息里只有列名)。EQP-2d 因此让服务端
   动作【自己】先抛具名码(`MAINT_DATE_REQUIRED` 等),表上那条 `NOT NULL`
   退成第三层兜底。**也就是说"拒空"这一族已经是两套机制并存了。**

### 删除条件

给这三张表各配一组 RPC(`record_equipment_maintenance` / `open_equipment_downtime` /
`close_equipment_downtime` / `save_equipment_service_interval`),把 CHECK 换成
函数里的具名 `RAISE EXCEPTION`,`equipmentErrorCodes.ts` 退回本仓库通用的
`CODE|参数` 形状。**约束本身留着**(它们挡的是直连那条路),但屏幕不再依赖它们的名字。

**为什么 EQP-2d 没有顺手做:** 那是一支迁移 + 四个函数 + 镜像 + fixture,
而 2a/2b/2c 三刀都是按"表 + RLS"这个形状建的。**改写入路径是一次设计变更,
不是一次上屏** —— 在一次刚被它绊到的切次里现写四个新函数,正是本仓库
「匆忙写出来的检查」那一课的另一个版本。

## 线上【八行物料全部改不动】—— PROC-1 的 NOT VALID CHECK,自 2026-08-21 起(PROC-5 撞出来的)

**是什么**:`materials_kind_stated` 是一条
`CHECK (kind_code IS NOT NULL AND may_be_processed IS NOT NULL) NOT VALID`。
PROC-1 刻意**没有回填**种类(D7:不为了满足约束而编造值)。

**而 NOT VALID 的 CHECK 与 NOT VALID 的外键【行为不同】,这一点此前没有人写下来:**

| | 旧行改【别的字段】 | 旧行改【那一列】 | 新行 |
|---|---|---|---|
| NOT VALID **外键** | 也被拒(RI 触发器不带列清单,实测 `tgattr` 为空) | 拒 | 拒 |
| NOT VALID **CHECK** | **被拒 —— 整行重算** | 拒 | 拒 |

两者都比"只管新行"这句常见的说法**严厉**。结果:

> **线上 8 行物料,8 行违反那条 CHECK,因此【现在一行都改不动】** ——
> 改名字、改安全库存、改备注,一律 `ERROR: violates check constraint
> "materials_kind_stated"`。**实测 8/8。**

**它是怎么被发现的**:PROC-5 要把一行的 `chemistry` 置空,迁移当场被拒(单事务,
整支回滚,零损伤)。**没有任何门看得见它** —— gate 三判词全绿,冒烟全绿:
这两样都不【改】既有业务行,而这条约束只在改的时候咬人。

**不是本刀修的,理由也写下来**:修它要有人说出每一种物料是什么种类、许不许投料
—— 那正是 PROC-1 的 D7 拒绝替人做的判断,也正是 PROC-3 报告里那句
"线上加工从 2026-08-21 起就全关着"的**同一个根因**。
**两件事一起解决:有人把八行物料的种类填了,加工的闸和物料的编辑同时活过来。**

**PROC-5 怎么绕过它的(不削弱任何东西)**:迁移里把那条 CHECK 卸下、改完、
**原样(仍然 NOT VALID)装回去**。它本来就不声称旧行合规,只声称新行必须合规,
卸下再装回前后逐字相同(线上核对:`convalidated = f`,与之前一致)。

## JE-APPEND · 往一张【已过账】的凭证追加明细(GO-2,2026-08-23 实测)

**GO-2 关上了这件事的【期间锁】那一半;另一半还开着,而且它要的根本不是期间锁。**

### 实测

以一个持 `module.finance.edit` 的真实 `authenticated` 用户,直接向 `journal_lines`
插入两条借贷相等的明细,父分录是**线上一张已经过账的真凭证**(2026-07-31):

```
借方合计  69,422.73  →  70,199.73
```

没有新分录、没有新凭证号,余额触发器照过(追加的一对本身是平的),
不变性触发器也没响 —— `trg_journal_lines_immutable` 守的是 `UPDATE`/`DELETE`,
**`INSERT` 不在它的管辖里**。

### GO-2 关上的那一半

那张分录的日期落在锁定期内,所以 `trg_journal_lines_period` 从此按码拒绝
(`PERIOD_LOCKED`),年结之内同理(`YEAR_CLOSED`)。fixture 122 的 F2c 臂钉着它。

### **还开着的那一半**

> **在一个【开着的】期间里,往一张已过账的凭证追加明细仍然成立。**

期间锁在这里【从来不是被违反的那条规矩】—— **不变性才是**。一张凭证一旦过账,
它的金额就不该再动;GO-2 之前它能动,GO-2 之后它在关着的期间不能动、
在开着的期间照旧能动。**这不是把洞补了一半,是两个洞长得像而已。**

### 它要的规矩,以及为什么不在 GO-2 里做

规矩是:**明细只能在【创建该分录的那一笔事务】里插入。**

这不是一行判据。`now()` 在一笔事务里是常量,**排不出事务内的先后**,
所以"这条明细是不是跟分录一起写的"问不出来 —— 本仓库遇到这个形状时反复
reach 的是一个**上下文标记**(`evoltrya.close_ctx`、`movement_ctx` 是现成的两个
先例:由写入方在同一事务内 `set_config(..., true)`,用毕即清)。

**它会住在哪:** `post_journal_entry` 在插入分录之后、插入明细之前设标记;
`guard_journal_line_period`(GO-2 刚建的那个触发器)多问一句 ——
没有标记、或标记指的不是这张分录,就拒绝。两处都已经在,所以改动面很小。

**为什么不在 GO-2 里做,而且这是刻意的:**

1. **它要一个判断,不是一次补漏。** 标记该记什么(分录 id?事务 id?)、
   合法的例外有没有(冲销、年结的两段式过账 —— `reopen_financial_year` 就是
   先过账后盖章)、以及**线上现存的明细全都没有这个标记**,所以新规矩只能对
   新写入生效 —— 那又是一次 `NOT VALID` 式的取舍。
2. **它会拒掉今天合法的写入路径**,而那些路径要一条条重新走过。GO-2 的两个
   触发器只拒【锁定期/已结年度】的写入,那是一条已经存在的规矩换个地方执行;
   这一条是**一条新规矩**。
3. 在一把刚被这个洞绊倒的切次里现写一条新规矩,正是本仓库写下过的那句
   ——「匆忙写出来的检查」的由来(WO-1a 的 pre-flight 那一条)。

**队列位置:** 与 `docs/forward-queue.md` 里「会计政策备忘录」同一批 ——
它是审计师会问的那一类问题(一张过账凭证还能不能被改)。

`suppliers` 与 `customers` 是两张**互不相干**的表:各自的主键、各自的编号序列
(`SUP-2026-xxxx` / `CUS-2026-xxxx`)、没有任何共用标识、没有任何列把一行指向另一行。
GO-4 给两张表各建了一个 `tax_id` 的部分唯一索引 —— **但那是两个独立的索引**,
同一个登记号在 suppliers 里出现一次、在 customers 里出现一次,**双方都合法**,
而且没有任何东西会指出这两行是同一家公司。

### 它的代价,说具体

* **两本分类账。** 应付挂在供应商那一行,应收挂在客户那一行。
* **两个余额,不会互相看见。** 一个既欠你钱又被你欠钱的对手方,在系统里是
  两个数字,人得自己去记住它们属于同一个人。
* **没有净额结算。** 真实世界里这种对手方常常轧差结清;这里做不到,
  而且**账龄报表把两边都当成完整敞口**,于是应收与应付同时被高估。
* **信用判断踩空。** `customers.credit_limit_base` 只看应收那一侧,
  完全不知道同一家公司在应付那一侧还挂着钱。

### 为什么不在 GO-4 里做

它**不是一个约束问题,是一个数据模型问题**。可能的形状至少三种(一张
`parties` 主表 + 两张角色表;一个跨表共享的对手方标识;或者把两张表合并),
每一种都要重新走一遍采购、销售、应收、应付、账龄与信用的每一条路径 ——
那是一次迁移加一轮全模块复核,不是一条索引。

**它也改变"重复"这个词的意思**,而这正是它必须先被裁定、再被实现的原因:
今天 GO-4 的规矩是"同一张表里同一个登记号只能有一行";这件事一旦有了答案,
规矩会变成"同一个登记号在系统里只能对应一个对手方,它可以有两种角色"。

### 返回条件

与 `suppliers.tax_id` / `customers.tax_id` 的必填一样,**批量导入那一刀**是自然的
时机:真实主数据到场时,同一家公司出现在两侧的情形会第一次真的发生,
而那时改的成本比现在低、比再往后低。

## GST:"孰早"那条规矩的【另一半】没有实现 —— 先于发票收到的客户款(2026-08-25 记录,GST-2)

**状态:按名拦住,不是无声放过。** 已注册时,一笔核销不到任何单据上的客户收款
被 `GST_UNALLOCATED_RECEIPT_UNSUPPORTED` 拒绝(`record_payment`)。

### 是什么
新加坡的供应时点是【开票与收款孰早】。GST-2 实现的是**开票**那一半。
收款那一半同样触发供应:一笔**先于任何发票**收到的客户款,在收到的那一刻
就是一个税点。这条路在本仓库是通的 —— `record_payment` 传空 `p_allocations`
会走 借银行 / 贷 1100,在应收上留下一笔贷余,那就是一笔客户预收。

### 为什么没有实现,而不是"没顾上"
**实现不了,而不是没时间。** 收款那一刻,系统里没有任何东西说得出这笔钱
对应哪一项供应 —— 于是税码、税率、进 F5 哪一格,三者都无从解析。
唯一的出路是**猜一个**,而猜一个税码与猜一个汇率是同一种谎:
它算得出数、报得出表,不会有任何一条报错。

### 为什么是"拒绝",不是"照收 + 记一笔待办"
照收的话,账上会留下一笔【已经触发了供应却没有报税】的钱,
而它看起来与一笔正常的挂账收款一模一样 —— 没有任何人会再想起它。
拒绝把这件事推到**收款发生之前**:先开票,再收款核销。
这也是这套账里本来就更正确的顺序。

### 删除条件
出现一种**在收款那一刻就说得出它对应哪一项供应**的单据 —— 例如一张
形式发票 / 预收单,它自己带税码与税率,收款核销到它上面。
那时这条拒绝换成对那张单据的正常处理。
**不接受**"收款时弹一个税码下拉让人现填" —— 那是把一个系统答不出的问题
转嫁给一个同样答不出的人,而他会填一个让屏幕变绿的值。

## GST-OFF-STRANDS-CODED-EXPENSES · 关掉 GST 会让带税码的费用单【再也冲销不了】(GST-3 实测,2026-08-25)—— **已挡住,但根因仍在**

> **⚠ 这一条【没有被修掉】,只是被一道闸挡在门外。把它读成"已修"会读错。**

### 实测(一次回滚掉的探针,不是推理)
开关打开 → 过一张带 `tax_code` 的分录 → 把开关关掉 → 冲销它:
`GST_NOT_REGISTERED|TX`。**那张分录再也冲销不了。**

### 根因,以及它是【今天早上自己引入的】
GST-2 让 `reverse_journal_entry_internal` 把 `tax_code` 一起翻过去 ——
不翻的话,一笔已冲销的进货会永远留在 box5,而总账本身是平的、看不出问题。
**那个修复是对的。** 它的副作用是:冲销从此**依赖开关的状态**,
而开关是可以关的。一个"忠实地复制原行"的冲销,继承了原行的全部前置条件。

### 处置:挡住,不是修掉
`trg_gst_switch` 拒绝在带税码费用单在册时关闭开关
(`GST_CANNOT_DISABLE_WITH_CODED_EXPENSES`,点名是哪几张),
并在 HINT 里给出唯一成立的顺序:**趁开关还开着先冲销,再关**。

### 为什么不直接放开冲销
"未注册时税码写不进任何地方"是 GST-1/GST-2 那条结构性保证的全部内容,
而它值钱正是因为它【没有例外】。给冲销开一个例外,等于把那条保证
从"做不到"降级成"通常不会发生" —— 而本仓库对这两者的区别付过账。

### 删除条件
出现一个**注销注册**(deregistration)的真实概念 —— 它有自己的生效日,
在它之后的单据不带税、在它之前的单据仍可按当时的注册状态冲销。
那时"关开关"不再是一个布尔翻转,而是一个有日期的事件,这一条随之消失。
**不接受**"关的时候顺手把税码抹掉" —— 那是在改写已经过账的历史。

## ~~SMOKE-QUERY-BLIND · 冒烟【从不发查询串】,于是查询参数后面的一切对每一次跑都不可见~~ —— **已收窄(2026-08-26,GST-FIX-1)**

## 银行对账:本刀【没有】做的两件,按名记下(BANK-REC,2026-08-26)

### 一 · 报表之间的【连续性】没有检查

`bank_statements` 同时记着 `opening_balance` 与 `closing_balance`,而
`import_bank_statement` 在门口强制 `opening + Σ 行 = closing`(单张报表内部自洽)。
**没有任何地方检查:这一张的 `opening_balance` 是否等于上一张的 `closing_balance`。**

**它会抓到什么:漏导入一个月,或者同一个月导了两次。** 两者都会在余额上留下一个
接不上的断口,而今天的每一张报表各自都自洽,所以谁也不会响。

**为什么不在 BANK-REC 里做:** 它是**另一条规矩,关于另一对对象** ——
本刀那条比的是"一张报表的期末 vs 那一天的账面",这条比的是"两张报表之间"。
把它塞进来就是在一次对账收口里夹带第二条拒绝,而没有人要求过它。

**返回条件:** 第一次真的漏导或重导一个月;或者银行对账下一次被打开时。
**做的时候要注意的一点(现在写下来,免得那天重新推一遍):**
第一张报表没有前一张,所以这条规矩天生有一个"起点"分支 ——
它必须是一个**具名的起点**,不能是"前一张为空就跳过检查",
否则每一个账户的第一张报表都是一个免检的洞。

### 二 · 冲销分录会永远留在匹配工作台的候选清单里

一笔在银行科目上被冲销的分录:原分录翻成 `reversed`(候选清单正确地排除它,
`match_bank_line` 也会拒),而**那张冲销分录本身是 `posted`,于是它一直是候选**。
如果这笔钱现实中根本没动过(记错了才冲销的),银行对账单上就没有对应的行,
于是**它永远配不掉,也永远从候选清单里下不去**。

今天没有"忽略一条分录行"的动作 —— `ignore_bank_line` 忽略的是**报表行**,
不是分录行。**所以这是一条会慢慢积攒的噪声**,而不是一个错数字。

**为什么不在 BANK-REC 里做:** 要么给分录行加一个"与银行无关"的标记(一张新表、
一条新动作、一条新权限),要么让冲销对里的两条互相抵消着从清单里消失
(而那会与 `match_bank_line` 的 `JL_ENTRY_REVERSED` 打架)。两种都是设计决定,
不是收口。

**返回条件:** 候选清单第一次因为这类残留而变得难用(一个可测的信号:
`bank_unmatched_journal_lines` 里属于 `source_type` 为冲销来源的行数);
或者有人问"这条为什么一直配不掉"。
