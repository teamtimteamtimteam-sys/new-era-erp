# 落地成本的【解除】:注销、盘点,以及回滚(PROC-COST-2,2026-08-31)

`docs/proc-cost-capitalisation.md` 讲的是成本怎么**进**存货。这一份讲它怎么**出来** ——
而上一刀交出去的那个发现正是:**它出不来。**

**本刀三件事都是更正,不是新功能(R2)。** 没有新科目、没有新报表、没有新屏幕。
三件事同属一个缺陷族:**资本化进存货的成本,系统要么看不见它、要么放不出来。**

---

## 一 · 裁定 R1 与它的科目映射

> **R1(Tim)· 一批料被注销或在盘点中盘亏,它的全部落地成本一次解除** ——
> 采购价 + 运费 + 已资本化的加工成本,全部转入损失。
> **不许为一批已经不存在的货在存货里留下任何东西。**
> 注销与盘点必须【一起】改:只改一个,两者就会对"这批货值多少钱"给出两个答案。

**科目一个都没换。** 逐条对过之后,答案是"改之前的映射本来就是对的,错的是金额":

| | 借 | 贷 |
|---|---|---|
| 注销 / 盘亏(进料批) | `5200` 存货调整损益 | `1200` 存货-原料 |
| 盘盈(进料批) | `1200` | `5200` |
| 产出批那一臂 | **一个字没动** | 载体只挂在进料批上 |

### 为什么贷方仍然是 `1200`,而且不会把它打成负数

这不是一句"看起来对",是一段可以复核的算术。**三个成本组件在入账时都只把
【在库份额】记进 1200**,已消耗的那部分当场进 `5000`:

* 计价:`reprice_inbound_batch` 拆 `in_stock_ratio`,在库进 1200、已耗进 5000;
* 运费:`record_freight_document` 同形拆分;
* 加工成本:资本化时那批料还在(状态改变型**不扣库存**),整额进 1200。

此后每一次消耗(`allocate_processing_costs` 的材料成本表达式)都按**同一个单位
费率**从 1200 解除。于是任意时刻:

> **1200 上属于这批货的余额 ≡ 单位落地成本 × `remaining_qty`**

而注销/盘亏解除的正是 `单位落地成本 × 变动量`。**整批注销 → 恰好归零,不会过头。**
fixture 161 的 A 臂断言的就是这个 0。

### 为什么 `5200` 不按原因拆成多个损失科目

**因为那是一个功能,而 R2 不许。** 全库今天只有一个 `5200`「存货调整损益」
(`is_system`,`cogs`)。按"报废 / 丢失 / 减值"拆开,需要的是**一套原因分类法** ——
新科目、新枚举、新的录入口、以及一条"哪个原因走哪个科目"的裁定。
一条都还没有被问过。

**写在这里,是因为单独一个损失科目读起来像疏漏。** 它不是:它是今天被问过的
问题的完整答案。

## 二 · 分母是 `quantity`,而这一段是本刀最该被复核的一处

单位落地成本 = `unit_price` + (运费 + 加工成本) ÷ **`quantity`**。

**(a) `÷ quantity`(本刀采用)** —— 与 `allocate_processing_costs` 材料成本表达式
**已经在用**的分母逐字相同(`batch_freight_base(ib.id) / ib.quantity`)。
消耗与注销因此恰好互补,整批注销净得零。

**(b) `÷ basis_qty`(载体行自己的处理量)** —— 听起来更对,**实际会把 1200
打成负数**:一张只处理了 100kg 中 30kg 的单,费率 500/30,整批注销解除
1,666.67 而 1200 上只有 500。而且它要把 `allocate_processing_costs` 一起拖进来改,
**为了一个更坏的答案**。

### 残差,明写,不做无声的缺口

把成本资本化到一批**已经被消耗过一部分**的料上时,`÷ quantity` **少解除**,
余额搁浅。**这个不精确是从材料成本表达式继承来的,不是本刀造成的** ——
消耗那条路用同一个分母,同样少解除。

真正的修法需要**子批身份**(这批 100kg 里的哪 30kg 被放过电),而载体表按
`inbound_batch_id` 记地址,表达不了它。**那是一个功能,不是一次更正。**
带实测形状记在 `docs/known-issues.md` 的 `LANDED-DENOM` 条。

## 三 · ★ 盘点【两个方向都改】—— 这是让这次修复安全的那一半 ★

`post_stocktake` 的盘盈与盘亏共用同一个 `v_value`。**只改盘亏那一边会怎样:**

```
盘亏 50kg → 解除 450(落地成本)
盘盈 50kg → 只补回 250(采购价)
────────────────────────────────
净:永久销毁 200 的运费与加工成本
```

而那批料**一克都没有离开过厂房** —— 有人点少了,又点回来了。

> **那是一次修复造出来的新缺陷,而它比被修的那个更坏。**
> 原来的缺陷是"少解除",这个是"凭空销毁"。

**所以两个方向同一个费率。这不是范围扩张,是这次修复能不能成立的条件。**

**实测基线:** 改之前 100 → 50 → 100 的净额是 `0.00`(两边都按 `unit_price`,
错得一样所以对消);改之后仍然是 `0.00`(两边都按落地成本)。
fixture 161 的 C 臂钉住它,并且**先断言盘亏那一步确实按落地成本走了 450** ——
否则这一臂可能靠"两边都错得一样"通过。

## 四 · 计值【不能】读那两个带权限判据的读取器

`batch_processing_cost_base` 对无权读者返回 NULL(PROC-COST-1 fu2),本刀让
`batch_freight_base` 也这样(第六节)。**而一笔要过账的计值绝不能读它们:**
那样"这批货值多少钱"就取决于**谁按的按钮** —— 一个只有 `module.inbound.edit`
的仓管按下注销,`COALESCE(NULL, 0)` 会让它安静地退回按 `unit_price` 计值,
**也就是本刀正在修的那个缺陷原样复发,而且再也没有人看得见。**

处置:**把算术与受众拆成两层,各自只有一份定义。**

| | 判据 | 无权时 | 谁读它 |
|---|---|---|---|
| `batch_freight_base_all` / `batch_processing_cost_base_all` | **无** | 不适用 | **计值**:`inbound_batch_landed_unit_cost` |
| `batch_freight_base` / `batch_processing_cost_base` | 有 | **NULL(受限)** | **屏幕**:批次页的落地成本拆解 |

`_all` 那一对是 `SECURITY DEFINER` 且没有调用者检查 —— 于是它们对
`authenticated` **不可执行**(`db/views/zzz_function_grants.sql`,理由写在那里),
靠的是"调不到"。gate 的 B2 认这条出路。

**一份实现,两个调用者:** `inbound_batch_landed_unit_cost` 是注销触发器与
`post_stocktake` **共用**的那一支。各抄一遍就是两次漂移机会 —— 而 R1 要求两者
一起改,理由正是它们必须永远给出同一个答案。fixture 161 的 D 臂断言这一点:
整批注销解除的金额恰为半批盘亏的两倍。

## 五 · 转化型回滚:三处不对称,一次全补,而且是【同一段代码】

上一刀只为**状态改变型**加了资本化的解除,并把转化型写成一条明写的待办。
实测,一张转化型加工单回滚之后留下:

| | 留下了什么 | fixture 162 |
|---|---|---|
| (i) | **资本化分录**(借 1220 / 贷 1200 / 贷 5xxx)原样立着 —— 产出批已软删,1220 上却还挂着它的成本 | A |
| (ii) | 重分摊的**差额分录**(`allocation_snapshot->'delta_entry_ids'`)同样立着 | B |
| (iii) | `capitalization_entry_id` / `capitalized_cost_base` **没有清** —— 一张已删的单还指着一张已冲销的分录 | D |

**(ii) 是最坏的一种半修:** 只补 (i) 的话,一张**被重分摊过**的单仍然错,
而它对没被重分摊过的单是对的 —— **于是它看起来已经修好了。**

**一个机制,不是两条路。** 原来那段冲销包在 `IF v_sc_kind` 里;本刀把那个判断
**拿掉**,让同一段代码管两种工序,再在其后补上差额分录那一圈。
fixture 162 的 E 臂断言状态改变型的行为**一个字没变** —— 一个"给转化型另写一条
路"的实现能通过 A–D,而两条路从此开始漂移。

### 第四个候选:`sales_records` 上的 COGS 分录 —— 不需要任何处置

`rollback_processing_run` 第 2 步的 `OUTPUT_CONSUMED` 闸在**任何产出动过之后**
就拒绝回滚,而一次销售必然动 `remaining_qty`。
**够不到的东西不需要修,但需要被点名** —— 否则下一个读到这里的人会把这条推理
重做一遍。它没有 fixture 臂,因为它没有可达的路径可钉。

### 与注销触发器的一处必须一起读的改动

产出批被软删时,注销触发器在 `reversal` 上下文里**不写分录**。
它原来的理由是「void 的产出从未入过 1220」—— **那句话在有了分摊之后就不对了**,
已分摊的产出批确实入过 1220。但**结论仍然成立,只是理由换了**:
解除 1220 的是这里冲销的那张资本化分录,**两处都做就是重复计数**。
函数体里的注释已经改成新的理由。

## 六 · `batch_freight_base` 的读者缺陷,与它为什么现在才成立

FRT-1 fu2(2026-08-11)把它**改回** `SECURITY INVOKER`,理由写得很清楚:
它只读 `freight_allocations` / `freight_documents`,而那两张表的 SELECT 策略
就是 `inbound.view OR finance.view` —— 守卫跟着数据自己的 RLS 走(OPS-15)。

**那个理由在当时是对的,因为那时读它的只有运费自己那批人。**
PROC-COST-1 在批次页上摆出了落地成本拆解,于是**一个只有
`module.processing.view` 的读者第一次会去调它** —— JOIN 把每一行丢掉,
函数安静地返回 0。

> **照抄一个先例之前要问那个先例成立的条件在这里成不成立** —— 而这一次,
> **是【后来的一刀】让一个成立的条件失效的**,不是当初抄错了。
> 这是同一条规矩的第二种形状,值得单独记:一个正确的判断会被别处的改动作废,
> 而它不会自己报错。

**处置(OPS-14 处置表的 (a) 支):** 属主权限 + 把读者的判据写进函数体,
无权返回 **NULL 而不是 0**。

### ★ 白名单里那一格 `module.processing.edit` 是承重墙,不是宽松 ★

`allocate_processing_costs` 的材料成本表达式把这支函数写在一个**加法**里:

```sql
quantity_consumed * (COALESCE(ib.unit_price, 0)
                     + batch_freight_base(ib.id) / ib.quantity
                     + batch_processing_cost_base(ib.id) / ib.quantity)
```

一个 NULL 加数让整个加数变 NULL,`quantity_consumed * NULL` 是 NULL,
**`SUM` 于是跳过整条投料腿 —— 连它的 `unit_price` 一起。**

**实测(fixture 163 D 臂,注入一个窄白名单):材料成本从 `750.00` 掉到 `0.00`。**

> **白名单开窄一格,一个【显示】缺陷就变成一个比它更坏的【计值】缺陷。**

`allocate_processing_costs` 第一行就是
`require_permission('module.processing.edit')`,所以它的调用者**必然**持有它 ——
白名单与 `batch_processing_cost_base` 逐字相同,理由也逐字相同。

**今天为什么没有出事:** `allocate_processing_costs` 是 `SECURITY DEFINER`、
属主是 `postgres`,而 `postgres` 有 `rolbypassrls` —— 于是 INVOKER 版本在它体内
读得到全量。**这个缺陷今天只伤屏幕,不伤账。** 而把函数改成属主权限 + 体内判据
之后,`has_permission` 读的仍然是**真实调用者**的 claims,`rolbypassrls`
不再兜底 —— 所以白名单从这一刻起成为承重结构。**这一段是本刀最容易做坏的地方。**

## 七 · 每一条【解除存货价值】的路,逐条走过

**结论短得出人意料,而那本身就是它值得写下来的理由:能直接卖掉一批进料批的路
【不存在】。** 下一个读的人可以照着这张表重新核一遍,而不必相信这句话。

| 路 | 计值依据 | 本刀 |
|---|---|---|
| 注销(`emit_batch_writeoff_movement` 进料臂) | ~~`unit_price`~~ → **单位落地成本** | **改** |
| 盘点(`post_stocktake` 进料臂,**两个方向**) | ~~`unit_price`~~ → **单位落地成本** | **改** |
| 加工消耗(`allocate_processing_costs` 材料成本) | 三项俱全(PROC-COST-1 起) | 未动,已正确 |
| `ship_order` | 产出批 `unit_cost_base` | 只碰产出批 |
| `record_output_sale` | 产出批 `unit_cost_base` | 只碰产出批 |
| `reserve_stock` | 不动价值,只换桶 | 不适用 |

后三条**一次都不提 `inbound`**(实测:`grep -n 'inbound' db/functions/ship_order.sql`
与 `record_output_sale.sql` 各 0 行)。产出批的 `unit_cost_base` 本来就已经
把投料的落地成本吃进去了 —— 走的正是上表第三行那条路。
