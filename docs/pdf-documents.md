# 对外单据(PDF)—— 共享版式、字体规则、以及两条 R4 记录

**PDF-1(2026-09-02)。** 这份文档回答四个问题:*有哪些单据、谁收到它、版式由什么
决定、字体凭什么可以内嵌。*

> **判据贯穿全篇:这份东西【离不离开这栋楼】。**
> 离开的,必须自我介绍(字标 + 法定名称 + 公司资料),因为客户要拿它入账、
> 审计师要拿它溯源。不离开的,不必 —— 自己给自己看的东西不需要自我介绍。

## 2 · 语言政策:两条,刻意不同

* **签发给外部的商业单据一律英文**(发票、采购单、销售订单、报价单、送货单、
  贷项凭证)。收件人不是这套系统的用户,所以界面切中文时开出来的也必须是英文。
  文案硬编码,**不接 i18n**。
* **报表与可追溯报告跟随界面语言**。它们是"应某个人的要求、在他面前生成的一份说明",
  而决定语言的正是生成它的人此刻读得懂的那一种。表头块会**印出它是用哪种语言渲染的**,
  所以一份中文档案不会被误认成"发错了语言的英文件"。
* 对账单跟随界面语言 —— 它由界面选出措辞后传进文档(`d.t`)。

**不要把一条规矩套到另一边。** 两者都是刻意的。

## 3 · 共享版式层 `app/components/pdf/`

落地前**七份 bespoke 文档各自 `StyleSheet.create` 了一遍几乎相同的东西**:
`page` / `title` / `code` / `metaRow` / `metaLabel` / `metaBlock` / `tableHeader` /
`row` / `cell` / `footer`,数值只差一点点(padding 36 与 40 两种;metaLabel 宽
90/100/110 三种)。`tableHeader` 与 `row` **在其中五份里逐字相同**。三份还各自
写了一遍同一个 `money()`。于是"改一下表格分隔线的颜色"是一件要动七个文件的事。

| 文件 | 管什么 |
|---|---|
| `theme.ts` | 品牌色、页面尺寸、`money()` |
| `fonts.ts` | **字体注册与字体栈**(见 §4) |
| `Wordmark.tsx` | 字标,**矢量**,从 `public/brand/evoltrya-wordmark.svg` 读 |
| `DocumentChrome.tsx` | `docStyles` + 抬头 / 表头 / 页脚三个组件 |
| `company.ts` | 取公司抬头的一处实现 + 交给守卫的字段清单 |

**为什么是"一组零件"而不是一个 `<DocumentShell>` 包住一切:** 八份单据的骨架真的
不同(发票有付款账户块与作废水印,采购单有付款里程碑与承诺定价条款,送货单有受控
废物分类栏,对账单是结转式摘要 + 账龄分档)。硬压成一个组件只会得到一个包着八份
实现的 switch —— 那正是 `CompanyLetterhead` 抬头写下的那条分寸(抽**内容与规则**,
不抽**每一处版式**)。

### 3.1 字标是矢量的,而且只有一份真源

`Wordmark.tsx` 在模块加载时**读那个 SVG 文件**,不把 8 条路径抄成 TSX 常量 ——
抄一份就是让品牌资产有两份副本,改了 SVG 而 PDF 还印着老字标不会有任何东西报错。
`@react-pdf/renderer` 的 `Image` **不支持 SVG**,但 react-pdf 4.5.1 **原生支持
`<Svg>`/`<Path>`**,所以这是最直的一条路:矢量、无格式转换、放大不糊。

**它拒绝它画不对的东西:** 解析只认"扁平的一组 `<path>`"。SVG 里出现 `<g>`、
`transform`、渐变或 `<image>/<text>/<use>`,**当场抛错**,而不是安静地少画一块。
一份印着残缺字标的发票,在生成时看起来是完全成功的。

### 3.2 ★ 上传的 logo 不再印在对外单据上 ★

**这是渲染出来才发现的,不是设计时想到的。** 加上共享抬头之后的第一次渲染里,
**字标出现了两次**:一次是矢量字标(品牌色),一次是 `company_profile.logo_path`
那张图 —— 而那张图**就是同一个字标的单色位图**,还更大、居中、把版面顶开了。

处置:R1 点名字标是 `public/brand/evoltrya-wordmark.svg`,所以留矢量那一份。
**`logo_path` 字段没有删**,`/finance/company` 仍然可以上传与显示它;
变的只是**对外单据不再印它**。三条路由里那段"从私有桶下字节、转 data URI"
也一并删掉了 —— 它已经成了一次**没有人会看的存储下载**,每渲染一次白花一次往返。

> 哪天真要在单据上印一个**与字标不同**的标记,那是一个新决定,应当带着它自己的
> 理由回来 —— 而不是因为这个字段恰好还在。

### 3.3 页码

落地前**八份里只有两份印页码**(发票、销售订单)。一份多页的对账单或采购单散在
收件人桌上时,**没有任何办法知道少了哪一页**,而对账单是最容易多页的那一份
(明细行没有上限)。现在页码由共享页脚给,格式统一为 `Page N of M`。

## 4 · ★ 字体:两个家族,一个栈,按字符选 ★

**R2:正文与数字用 Google Sans,中文用既有的中文字体。**
落地成 react-pdf 的一个**字体栈**:

```ts
fontFamily: DOC_FONT_STACK        // ['Google Sans', 'Noto Sans SC']
```

排版引擎(`@react-pdf/textkit` 的 `pickFontFromFontStack`)对**每一个码位**依次问
`hasGlyphForCodePoint`,取第一个画得出来的。所以 `INVOICE`、`1,234.56` 落在
Google Sans,`上海金属回收` 落在 Noto Sans SC —— **同一个 `<Text>` 里混排也成立**,
这是逐字符的,不是逐节点的。

**Google Sans 没有中文**:实测它服务端下发的 TTF 共 **3281 个码位**,CJK 统一表意
文字**一个都没有**。这不是"暂时没配",是这个家族的覆盖范围。

### 4.1 ★★ 两个字重都必须注册 ★★

实测:只注册 Google Sans 400、再写 `fontWeight:'bold'` 时,拉丁拿不到粗体 →
引擎退到 **Noto Sans SC Bold**,于是**同一行里拉丁是细的、中文是粗的**。
它看起来像渲染器的毛病,不像"少注册了一个字重",所以会被诊断到别处去。
`fonts.ts` 因此在**模块加载时**断言每个家族都有 `normal` 与 `bold`,缺一个就抛错。
**字体没装好属于部署事故,该在冷启动炸掉,不该等某个客户的某张发票渲染到一半。**

### 4.2 ★ 许可:Google Sans **可以**内嵌进对外分发的 PDF ★

这些 PDF 寄给客户与审计师,**那是分发**,而分发内嵌与网页使用是两回事。
四份出处,由硬到软:

| 出处 | 结论 |
|---|---|
| **`OS/2.fsType` = 0**(读的是 Google 实际下发、且**裁剪之后**的那份 TTF) | **Installable Embedding —— 无限制**。这正是 PDF 生产端读的那个字段 |
| 同一份二进制的 name ID 14 | `https://openfontlicense.org` |
| `github.com/googlefonts/googlesans` | SPDX **OFL-1.1**;OFL 的 PERMISSION 段**明文列出 `embed`** |
| Google Fonts metadata API | `license: "ofl"`,`isOpenSource: true` |

OFL 还把文档那一侧说死了:

> *"The requirement for fonts to remain under this license does not apply to any
> document created using the fonts or their derivatives."*

**所以 PDF 本身不承担任何署名义务。**

**没有保留字体名(RFN)。** `TRADEMARKS.txt` 明说 Google 刻意不在版权声明里放
RFN。这一条**直接决定本刀能不能裁剪**:裁剪产出的是 OFL 意义上的 "Modified
Version",若有 RFN 就必须改名。没有,所以可以裁剪并沿用原名。

**商标那一条仍然成立、但与本用法无关:** 不得把 "Google" / "Google Sans" 用作
公司名、产品名、域名或社交账号名。本仓库没有这么做。

`subset.py` 在**每一次裁剪后的字节上**重新读 `fsType`,不是相信源文件那一次;
读到禁止内嵌的值就**退 2 并停下**,而不是换一个字体蒙混过去。

### 4.3 裁剪与覆盖清单

| | 完整 | 裁剪后 | 覆盖 |
|---|---|---|---|
| Google Sans Regular/Bold | 各 1.9 MB | **各 0.05 MB** | 233 码位(拉丁 + 标点) |
| Noto Sans SC Regular/Bold | 各 10.5 MB | 各 2.20 MB | 7276 码位(GB2312 + 中文标点 + 拉丁) |
| **栈合计** | | **≈ 4.5 MB** | **7290 码位** |

**★ 对"这些单据印得出什么字"的净影响,量过 ★**

* **失去:0 个。** 改造前印得出来的每一个字符,现在都还印得出来。
* **新增:14 个**,全部**看得见** —— 9 个不同宽度的空格,以及 `‱ ⁃ ⁄ ⁎ ⁕`。

新增数原本是 **28** 个。另外 14 个是**看不见的格式控制符**(`Cf` 类),包括
`U+200B–200F` 零宽字符、**`U+202A–202E` 双向嵌入与覆盖**、`U+2066–2069` 双向隔离。
**`U+202E` 能让一段文字在阅读器里反着显示。** 改造前守卫会拒掉带这种字符的单据,
改造后就不会了 —— 而那是一个**没有人要求过的放宽**,于是两个家族都不收 `Cf`。

> **`U+00AD SOFT HYPHEN` 是这条规则的唯一例外,而它是量出来的。**
> 排除 `Cf` 的第一版把它一起排掉了,覆盖清单从 7276 掉到 7275 —— 一个
> **改造前印得出来、改造后被守卫拒掉**的字符,也就是本刀造成的收窄。
> 两条理由让它留下:① react-pdf 的排版引擎**本来就不给它取字形**
> (`IGNORED_CODE_POINTS = [173]`),有没有字形对渲染毫无影响;
> ② 它今天就在清单里,含它的单据今天渲染正常 —— 守卫拒掉一份能正常渲染的单据,
> 是"永远不可能被满足的判据"的另一种形状。

`coverage.json` 现在**逐家族**记录覆盖,外加一个**并集**顶层 `ranges` ——
守卫查的就是并集,因为**文档嵌的是整个栈**。

## 5 · ★★★ 对账单那个缺陷 —— 一道查错了对象的守卫 ★★★

> **`StatementDocument.tsx` 把 page 写成 `fontFamily: 'Helvetica'`,另有六处
> `'Helvetica-Bold'`。Helvetica 是 PDF 内置字体,一个汉字都没有。**

实测渲染复现:`上海金属回收有限公司` 印出来是 **`wÑ^Þ6 Plø`** ——
**不是空白、不是豆腐块,是一串看起来像模像样的重音拉丁字母。**
一个扫一眼的人会以为那是某个奇怪的名字,不会以为是故障。**这就是它没被发现的原因。**

**而这条路由【调了】字体覆盖守卫,守卫每一次都通过** —— 因为守卫查的是
**Noto Sans SC 的覆盖清单**,而文档嵌的是 **Helvetica**。
**一个标签与判据问的不是同一件事的检查。** 这是本仓库记过多次的那一族。

**规矩当时已经写下来了,写在发票文档里,而它没有拦住任何人:**

> 「凡是要加粗的地方一律用 `fontWeight: 'bold'`(而不是 `fontFamily:
> 'Helvetica-Bold'`),否则等于把那个节点换回了拉丁字体。」

**范围,照直说:** 落地时 `customer_statements` **0 行**,且线上**没有任何**客户 /
供应商 / 物料 / 备注 / 地址含中文(全部实测 2026-09-02)。所以它**还没有**糟蹋过
一份真的对账单 —— **它是一个装好了的陷阱,不是一场已经发生的事故。**
但对账单的全部用途就是寄给欠款人要钱,而第一个中文客户不会带着警告出现。

### 5.1 修法是两半,而**durable 的是第二半**

1. **可见的那一半:** 对账单改用 `DOC_FONT_STACK`,六处 `Helvetica-Bold` 换成
   `fontWeight:'bold'`。
2. **★ durable 的那一半:`scripts/check-pdf-font-stack.mjs`,进 `npm run build` ★**
   PDF 文档文件里 `fontFamily:` 的值**必须**是 `DOC_FONT_STACK` 这个标识符。
   写死家族名、写 `INVOICE_FONT_FAMILY`、就地重写一遍栈 —— 三种都红。
   **落地时它一次抓出 13 处**,其中就是对账单那 6 处 —— 也就是说
   **它写下来的那天就会拦住这个缺陷。**

   *它不查什么(说清楚,免得绿灯被读成"字体一定对"):* 它查的是**源码里写没写
   别的字体**。它不验证 `coverage.json` 与 `.subset.ttf` 对不对得上(那由
   `subset.py` 同一次产出保证),也不验证渲染结果的字形(那要真的渲染)。
   扫到 **0** 个 PDF 文件时它**退 2**,因为零必须是一次测量,不是一次沉默。

3. `lib/invoiceFontCoverage.ts` → **`lib/pdfFontCoverage.ts`**。落地时它已被
   **七条**路由调用,名字还写着 "invoice" —— 而名字决定下一个人以为这道守卫
   **管的是哪一份文档**。

## 6 · R4:两处"空白/零"代替了系统其实知道的事

R4 要求把这一类**报告**出来,而不是当成版式问题顺手改掉 —— 改它们会改变单据
**说了什么**(R3)。两处都是**在渲染出来的纸面上**确认的,不是读源码推的。

### 6.1 贷项凭证:数量栏是**空的**

`CreditNoteDocument` 写的是 `{l.qty === null ? '' : l.qty}`。
`revenue_reduction`(价格/品质调整)这类行**本来就没有数量** —— 那是
**"不适用"**,不是"没填"。而纸上印出来的是**一个空格子**,客户分不出
"这一行不涉及数量" 与 "数量漏填了"。
**实测:`CN-2026-0001` 的 Quantity 栏在渲染出来的 PDF 上是空的。**

### 6.2 库存快照 PDF:**没有成本口径的量印成 `0`**

`snapshotQuery.ts` 自己的注释写着:

> 【没有成本口径的量】进料侧"没有价",产出侧"从未分摊" —— **都不是"值 0"**。

它为此带了一列 `uncosted_qty`。**CSV 导出印了这一列;PDF 没有。**
于是 PDF 上 `Value (SGD)` 那一栏的 `0` **同时表示"真的值 0"和"没有成本口径"**。

线上实测(2026-09-02,以有权限的会话取 `inventory_valuation_snapshot`):

| 物料 | 口径 | 数量 | `value_base` | `uncosted_qty` | PDF 上印的 |
|---|---|---|---:|---:|---:|
| MAT-2026-0001 | inbound | 1 | 0.0 | **1** | `0` |
| ZZ-SMOKE-PROBE | inbound | 99970 | 0.0 | **99970** | `0` |
| MAT-2026-0001 | inbound | 14487 | 111834.36 | **1800** | `111834.36` |
| MAT-2026-0001 | output | 2528 | 253.34 | **2433** | `253.34` |

**前两行整批没有成本口径,纸上是一个 `0`。** 后两行更微妙:金额是真的,但它
**只覆盖了一部分数量**,而纸上没有任何东西说另一部分没有价 —— 一个读者会把
`111,834.36` 当成那 14,487 kg 的价值。

**没有在本刀里改。** 修法要在 PDF 上增一列或加一句话,而那是**改变这份文档说了
什么**,该由 Tim 决定,不该由一次版式改动顺手做掉。

## 7 · 证据:每一份都渲染过、看过

`scripts/render-pdf-samples.mjs` —— 起 dev server、建一次性 admin 会话、
用线上真数据把每一份单据落到磁盘。**它刻意不断言**:"版式好不好看""字标在不在"
不是文本判据能回答的,硬写一条只会得到一个看起来在把关、其实什么都没查的检查。
它的产物是**证据**,给人看的。

**11/12 渲染成功。第 12 份是对账单,`customer_statements` 线上 0 行** ——
**说出来,而不是让它在产物目录里与"渲染过"长得一样。**
