# 按角色走一遍:一个机制,不是两个(scoping,2026-08-10)

**结论先说:是一件事,你的判断对;规模是【中等偏大】,一天到两天的量,不是半天。
它能一次性补上两个缺口,而且是唯一会在 Tim 之前发现 /margin 的东西。**

## 两个缺口是同一件事的两半

| 现有工具 | 它回答的问题 | 它看不见的 |
|---|---|---|
| `scripts/smoke-routes.mjs` | 每条路由渲染得出来吗(以 **admin** 身份) | 守卫【太紧】—— admin 什么都有,所以一道错误地挡住 operations 的门,在 smoke 里永远是 200 |
| 本次的可达性走查 | 代码里【存在】一条路径吗 | 那条路径【对这个人渲染出来了吗】—— 导航按权限过滤、首页卡片按权限过滤、页内链接常在条件分支里 |

两者缺的是同一个东西:**以某个角色的身份,从 `/` 出发,只跟着他【真的看得见】的
链接走,看他到得了哪里。** smoke 有会话与渲染,却只有一个角色;可达性走查有图,
却没有渲染。把两者合起来就是这个机制。

## 形状

复用 smoke 已经有的机器(它已经会建一次性账号、授角色、拿 cookie、起 dev server):

1. **每个角色一次性账号**:live 有 10 个 active 角色。建号 → 授【单一角色】→ 登录取 cookie。
   单一角色是关键:admin 之外的每个角色都是一个独立的问题。
2. **从 `/` 抓 HTML,解析出真正渲染的 `href`**(不是源码里的 href,是 DOM 里的)。
   这一步就是与现有走查的分水岭:导航过滤、卡片过滤、条件分支全都已经发生过了。
3. **BFS**:对每个新 href 抓页面、断言状态码、再解析它的 href。动态段用 smoke 已有的
   "从库里取真实 id"的机制填。
4. **两侧断言**:
   * **可达但打不开** → 红。这是"导航给了一扇打不开的门"(OPS-15 拆掉的那类)。
   * **打得开但走不到** → 红(白名单除外)。这正是 `/margin` 对 `finance` 与
     `operations` 的形状:两人都进得去,但入口只在对方的模块里。
   * 期望集合按角色写进一份【断言文件】,像 `EXPECTED_SKIPS` 那样,drift 两个方向都失败。

## 代价,如实说

* **运行时间**:smoke 现在跑 134 条路由约 2–4 分钟。10 个角色即使各自只走得到平均
  三分之一,也是 3–5 倍的请求量 —— **十几到二十分钟**。所以它 **不能进 `db/gate.py`**
  (「慢的门就是被跳过的门」那条规矩),要么按需跑,要么进 CI 的夜间档。
* **数据准备**:每个角色要能看到【至少一条数据】,否则页面为空,链接不渲染,走查
  会把"没数据"误报成"不可达"。这是最容易做错的一半 —— 与 `EXPECTED_SKIPS` 同一个病:
  **一条从 ok 变 skipped 的路由,和一条本来就没数据的路由,长得一模一样。**
  实现上要么给每个角色准备一份 scratch 数据(smoke 已经会建 ZZ-SMOKE-* 员工),
  要么把"这个角色在这条路由上无数据"作为**显式声明**而不是推断。
* **HTML 解析**:不需要真浏览器 —— RSC 输出的是 HTML,`href="..."` 正则足够。
  客户端条件渲染(useState 之后才出现的链接)会漏,这是**已知边界**,要写下来
  而不是假装覆盖:属于 Playwright 的领域,而引入 Playwright 会把这件事从两天变成一周。
* **维护**:每个角色一份期望集合 = 10 份清单要跟着新页面走。缓解办法是断言
  **形状**而不是穷举:比如"operations 到得了 /processing 及其全部子路由",而不是逐条列。

## 边界(写下来,免得绿灯读成"全覆盖")

* 只测【渲染出来的链接】,不测"这个人是否**应当**看见这个入口"——后者是产品判断,
  仍然要人来定,机制只保证清单与现实一致。
* 客户端交互之后才出现的入口(下拉、弹窗、条件按钮)不在覆盖内。
* 它不验证页面**内容**对不对(INV-2026-0005 那类"数字标错币种"仍然逃得掉)——
  那是另一件事,上一轮已经记过:smoke 只断言状态码,没有任何东西比对页面上的数与库里的数。

## 建议的做法

**分两步,先拿到八成的价值:**

* **第一步(半天):把 smoke 从"一个 admin"扩成"admin + 两个窄角色"**(`operations`、
  `finance` —— 正是 /margin 那道题的两边),沿用现有的路由清单与期望状态,
  只加一条断言:**这个角色能打开的页面里,有没有他从 `/` 走不到的。**
  这一步就会点名 `/margin`,而且不需要 BFS 的全部机器。
* **第二步(一到两天):十角色全量 BFS + 每角色期望集合 + 夜间档。**

**它是一个真项目,不是一个下午。** 但第一步不是 —— 而第一步已经能抓到这次的问题。

## 后记:一个角色一跑(GUARD-FIX-1,2026-09-01)

上面设计的是"三个角色走一遍"。**跑了三周之后,它装不下了。**

| | 实测 |
|---|---|
| 2026-08-11(PUR-2,139 条路由) | 65 分 44 秒,1,018 次抓取(admin 走 337、operations 115、finance 281) |
| 2026-08-24(GST-1,189 条路由,隧道退化) | **超过 2 小时** |
| 2026-08-31(NAV-REG-1) | admin 一个人吃掉 90 分钟里的 **~63 分钟**;路由前沿爬到一半从 **475 涨到 563**;`finance` **被半路杀掉** |

**Tim 的裁定(R3):切,不是把上限调大。** 理由不是时长本身,是
**一条三小时的检查是一条没人跑的检查** —— 而这是唯一看得见
"打得开却走不到"的检查。GUARD-FIX-1 那两处丢掉的守卫活了四天,
正因为它们落地之后没有人跑得起 `--reach`。

**切的单位是【角色】,不是【阶段】。**
按阶段切(先三个角色全爬、再三个角色全试开)会得到
**两个永远不会红的半跑**:判据是 `unreachable = openable − seen`,
而这两个集合**必须来自同一个角色的同一跑**。按角色切是唯一还能出判词的切法。
谁将来想"优化"成阶段切,请先读这一段。

**用法:**

```
node scripts/smoke-routes.mjs --reach=finance   # admin | operations | finance
node scripts/smoke-routes.mjs --reach           # 三个全跑,约 100 分钟,推送前
```

### 每个角色要多久 —— 【比例外推错了一次,记在这里】

`admin ~63 分`、`operations ~17 分` 是 2026-08-11 量过的。
**`finance` 这一条本刀先用比例推成了 "~20–25 分",并据此把 `--timeout` 设成 3600s ——
推错了。** 实测爬的速率是 **10 页/分钟**(90 秒 15 页),finance 的前沿一路涨过 277,
光爬 ~30 分、逐条试开 ~15 分,加上前面路由那一半 ~17 分,**≈ 65 分**。
那一跑会在干完之前被上限砍掉,而那正是 GST-2 记过的那次误杀的同一个形状:
**上限从【估的成本】推,而不是从【量的成本】推。**
`run_detached.sh` 抬头那句"量过的成本还要真的被用进上限里"说的就是这件事,
而它这一次是被**重新犯了一遍**才生效的 —— 所以补在这里:
**不要拿抓取比例去推第四个角色的时长,去量它。**

**finance 的真数(本刀,2026-09-02):59 分 47 秒**(3587s,判词 `REACHFIN2_EXIT=0`)——
走到 **457** 页、试开 **145** 条静态路由、打得开 88 条、其中走不到 3(正是
`EXPECTED_UNREACHABLE.finance` 那三条,零漂移);路由那一半 231 ok / 8 skipped / 0 FAILED。
**爬的过程中前沿从 191 涨到 457**,与 admin 撑爆 90 分钟的是同一件事。

角色名拼错**响亮退出 2**,不会当成"零个角色要跑"悄悄打印一行绿;
`EXPECTED_UNREACHABLE` 缺条目的角色也在**开跑前**拒绝
(能在开跑前回答的问题就在开跑前回答 —— ID_SOURCES 预检付过的那一课)。
