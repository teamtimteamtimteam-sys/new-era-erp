# 加工成本资本化:载体、科目,以及那条【没有被用】的路(PROC-COST-1,2026-08-31)

上一刀(PROC-WIRE-1B-i)在这里停住,并且**停得对**。它留下的是一条按名拒绝
(`ALLOCATION_STATE_CHANGING_UNRESOLVED`)和一个写下来的理由。这一刀把那条拒绝
换成真正的去处。

---

## 一 · 裁定与科目映射

**R1 · 成本资本化进批次;没有产出腿时,收件人是【投料批】。**
这条原则不是新的:每一道工序的运营成本最后都落进产品成本。转化型工序把它落进
产出批(借 1220),状态改变型没有产出批 —— 于是收件人是那批**还在那里的**原料
本身。深度放电不产出任何新东西:料进去、料出来,只是不带电了。

**R2 · 科目:不新建任何科目。** 逐项对上了本仓库既有的科目表:

| Tim 说的 | 仓库里对应的 | 说明 |
|---|---|---|
| 生产成本 | `5100`–`5190`「加工成本-*」 | **它已经在承载这些成本了** —— `fin_journal_cost_entry` 在成本条目录入的那一刻就借 5xxx / 贷 2200。Tim 的裁定命名的是一个**概念**,而那个概念早已实现 |
| 资本化的去处(进料批) | `1200`「存货-原料」 | 放电不产出新东西,那批料**仍然是原料** |
| 资本化的去处(产出批) | `1220`「存货-成品」 | 转化型工序的既有路径,本刀未动 |
| ~~在制品~~ | `1210` | **一个字都没碰**:`is_system = false`、全库无人引用,那是建账的人的地盘 |

**R3 · `unit_price` 一个字节都没动。** 见第二节 —— 这是整刀最要紧的一段。

**A3 · 这不是一笔新成本进账,是一次【重分类】。** 电费早在录入那一刻就进了总账。
资本化这一步不新增任何金额,它把已经在销售成本里的钱**拨进存货**:

```
借 1200        （资本化到投料批）
    贷 5100/5110/…（逐 cost_type,fin_cost_account 映射）
```

正是既有 `借 1220 / 贷 5xxx` 的镜像,只是收件人不同。

## 二 · 为什么【没有】走 `unit_price` —— 这一段最值得留给后来的人

> **`inbound_batches.unit_price` 是【应付之锚】。**
> `ap_open_items` 按 `quantity × unit_price` **实时**算我们欠供应商多少钱。

于是两条看起来更省事的路,各自会造成什么:

* **把加工成本并进 `unit_price`** = **凭空捏造供应商债务**。我们自己烧的电,
  变成了欠材料供应商的钱。分录仍然是平的,应付账龄仍然算得出来,只是数字是错的。
* **走 `reprice_inbound_batch`** = 把一次加工记成一次**重新议价**,并在
  `price_history` 上留下一串**假的**过期标记 —— 而那张表是不可变的,
  写进去就再也拿不掉。

**所以成本载体与 `unit_price` 分开,估值读三项之和:**

```
落地成本 = quantity × unit_price      ← 采购价,欠【材料供应商】
         + batch_freight_base()       ← 运费,欠【货代】(FRT-1)
         + batch_processing_cost_base() ← 加工成本,【不欠任何人】(本刀)
```

三个组件、三个对手方(其中一个没有对手方)。这就是为什么它们必须是三样东西,
而不是一个更大的单价。

## 三 · 载体的形状:FRT-1 的形状,第二次使用

**这是刻意的复用,不是巧合。** 运费早已解决过同一个问题,措辞就写在
`db/migrations/2026-08-11-frt1-freight-capitalised-into-batch-cost.sql` 里:
"第二个成本组件,绝不并进 unit_price"。它的形状是

> **一张对批次记成本事件的台账** + **一个把它求和的派生函数**

而不是批次上的一列。照抄这个形状,两件要紧的语义**免费得到**:

* **累加** —— 一批货被放电两次 = 两行,`SUM` 天然累加,永不覆盖;
* **冲销即解除** —— 基函数只认**活着且已提交**的加工单,回滚把单软删,
  那一行就自动不计。

**一列做不到这两样**:它得读-改-写,而两次放电会互相覆盖。fixture 160 F1
就是钉这一条的 —— 一个"把载体做成一列"的实现在那里只剩第二笔。

### 与 `freight_allocations` 刻意的一处**不同**

`freight_allocations.amount_base` 有 `CHECK (amount_base >= 0)`;本刀的载体
**没有**。理由不是疏忽:运费永远为正(总是欠货代一笔钱),而
`processing_cost_entries` 明写 *"Deliberately no sign check: by-product /
disposal offsets may be negative"*。照抄那条约束,会让一笔在源表里合法的副产品
冲抵在这里撞墙。**形状照抄,理由不成立的约束不照抄。**

### 为什么**不**并进 `freight_allocations`

每一张运费单都指名一个**货代** —— 一个我们欠钱的对手方,未付即成为一行
`ap_open_items`。我们自己烧的电**不欠任何人**。把一个非应付项塞进一个整体形状
都假设有对手方的结构里,迟早会有人按那个假设去读它。

## 四 · ★ 一条被测量推翻的前提,原样记下 ★

本刀的委托书里写着"估值读采购价加已资本化加工成本"。这句话**假设存在一个估值口**。

**实测:不存在。**

* `batch_freight_base` 全仓库只有**一个**生产消费者 ——
  `allocate_processing_costs` 的材料成本表达式;
* `stock_snapshot` 只有数量,没有金额;
* `inbound_batches_masked` 只透 `unit_price`;
* `batch_margin` 读的是 `processing_outputs.unit_cost_base`,那只有产出批才有。

于是,**进料批上的资本化成本只有一条路能走到损益表:那批料后来被一张转化型
加工单吃掉**,材料成本表达式把它读进去,再随产出批的 `unit_cost_base` 流向 COGS。

> **一批放完电就再没被加工过的货,它身上的成本没有任何报表看得见。**

这与 FRT-1 为运费写下并接受的敞口是**同一个**,现在是**知情地**再接受一次,
不是漏掉。本刀因此在批次页上建了**落地成本拆解**(采购价 / 运费 / 加工成本 / 合计),
顺带把运费同样的隐身也一并解决了 —— 那是把这个数**给人看**的最小的东西。

**一张计值存货报表是另一刀,不是本刀留下的缺口。** 它要回答的是"按哪个口径计值"
(先进先出?加权平均?)以及"注销与暂扣算不算在内",而那些问题今天一个都没有被问过。

## 五 · 第七过期源:不可省

`processing_run_allocation_status.last_cost_change` 现在看**七**个来源。第七个是
本刀加的:一张状态改变型加工单把成本挂到某批进料上,而那批料**可能已经被别的单
吃掉了**。

不加这一臂,后果是本仓库最坏的失败形状:

> 吃过那批货的单永远不标过期,`batch_margin` 停在放电之前那个数,
> **而放电那张分录本身完全正确**。每一笔都对,总数错。

FRT-1 把漏掉同构的那一臂称作**"本刀的头号缺陷"**。这里不重犯,fixture 160 F5
两个方向都钉:注入前不过期,注入后过期。

**【排除自己】(`bpca.run_id <> r.id`)是防御性的,而这一点要说准:** `allocate`
在同一笔事务里写下载体行与 `allocated_at`,`now()` 是事务时刻,两者恒等、`>` 恒假 ——
所以**今天漏掉它也不会有人变红**。它挡的是将来有人把载体行的写入挪出这笔事务
(或换成 `clock_timestamp()`)之后,放电单永远举着一面自己造的旗。

## 六 · 换掉那条拒绝之后,还有哪些情形【仍然】拒绝

| 拒绝 | 什么时候 | 为什么不是"算成零" |
|---|---|---|
| `ALLOCATION_STATE_CHANGING_BASIS` | 状态改变型 + 金属价值基准 | 那个基准按**产出批的金属含量**拆分,而这里没有产出批 —— 不是"算出来是零",是**没有可读的数** |
| `ALLOCATION_STATE_CHANGING_OUTPUT_INPUT` | 投料里有**自产产出批** | 载体按 `inbound_batch_id` 记地址,产出批不在它的地址空间里。**按名拒绝,不许悄悄把成本丢掉** |
| `ALLOCATION_STATE_CHANGING_NO_INPUT` | 没有进料批投料 | 资本化没有收件人 |
| `ALLOCATION_LEDGER_DIVERGED` | 资本化分录被人工冲销 | 与既有路径同一条 |
| `BPCA_BATCH_NOT_AN_INPUT` | 一行载体指向**不是这张单投料**的批次 | 见第七节 |

**转化型少了产出仍然是 `NO_OUTPUTS`,一个字没松** —— 那道闸在 `commit` 上,本刀未动。

### 为什么状态改变型的重分摊可以【冲旧挂新】,而 FIN-24 对转化型禁止

这不是抄一条惯例,是一条**只在这里成立**的论证:

FIN-24 禁止转化型这么做,是因为成本已顺着产出批流向**已售份额**,而已过账的 COGS
从不重述 —— 卖得越多错得越多。**状态改变型没有产出批**:它的成本停在 1200 上
一批仍然是原料的货上,没有任何下游把它当成本消费掉。若那批料后来被一张转化型
加工单吃掉,那张单会因**第七过期源**而过期,重跑即修正。

## 七 · 那道闸:一行载体必须指向它自己那张单的投料批

走 `allocate_processing_costs` 天然不会挂错。但这张表对 `authenticated` **可写**
(RLS 放 `module.processing.edit`,与 `freight_allocations` 同形),
所以**"走那条路不会"与"不可能"是两件事**。

挂错的后果:成本跟着那批货走进**别人的**产出单位成本里,而每一张分录仍然是平的 ——
**错的是货,不是账**。跨两张表的规矩 `CHECK` 看不见,所以是触发器
(`guard_bpca_batch_is_input`,fu1)。

## 八 · ★ 一个只有 `module.inbound.view` 的读者会读到 0 —— 实测,已修(fu2)★

`batch_processing_cost_base` 起初是 `SECURITY INVOKER`,照的是 FRT-1 fu2 的先例
("一个金额读取器不该替调用者绕过 RLS")。而它的函数体里 `JOIN processing_runs` ——
**那张表的 SELECT 策略要的是 `module.processing.view`。**

于是一个只有 `module.inbound.view` 的读者(仓管、进料)在批次页上调它,
那个 JOIN 把每一行都丢掉,函数**安静地返回 0**。那批料身上明明挂着 500,
屏幕上写着 0。

**这正是 OPS-14 命名过的那一族:`colreader` 问【列】(读不到 → 42501,响亮);
`xmodule` 问【行】—— 读不到就无声消失。** 而 `0.00` 与「受限」不是同一件事:
第一个是谎话。本刀的验收条件恰恰是"操作员能在屏幕上看见这个数",
所以这条缺陷打在它最要紧的地方。

**处置(OPS-14 处置表的 (a) 支)**:属主权限 + 把读者的判据**写进函数体**,
无权时返回 **NULL 而不是 0**。

**照抄一个先例之前,要问那个先例成立的条件在这里成不成立。**
`freight_documents` 的策略是 `inbound.view OR finance.view` —— 与运费的读者是
同一批人,所以 INVOKER 在那里安全;`processing_runs` 是**另一个模块**,不安全。

> **白名单里含 `module.processing.edit` 是有原因的,不是宽松**:
> `allocate_processing_costs` 第一行就是 `require_permission('module.processing.edit')`,
> 所以任何走到那里的调用者**必然**持有它。于是材料成本表达式里这一支
> **按构造**不可能读到 NULL —— 而一个 NULL 会让 `SUM` 把整条腿跳过,
> 造出一个静默变小的材料成本。

## 九 · R4:鼓包漏液的去处

`operation_type_safety_states` 的表注里原本写着:

> "为什么 swollen_leaking 一道工序都没有受理 …… **于是这种料今天没有路线,
> 那是刻意的**,它等 Tim 的一句裁定,不等一个猜测。"

**裁定到了。** 鼓包与漏液**同一处置**,不拆成两个安全状态,走**整电池粉料线**,
与 `damaged_deformed` 完全同形 —— `resolves = false`:粉料线把料**粉碎掉**,
不是把鼓包治好。

**不变式一个字没松。** 加一行受理是**逐工序的、明写的数据**,那正是这张表允许的
唯一放宽方式。两条既有的坏实现在 fixture 159 里**仍然是红的**(本刀实测复核过):

* **按 kind 放行**(状态改变型一律受理)→ F3 红;
* **默认放宽**(`may_be_fed` 仍然算数)→ F2 红。

**深度放电仍然拒绝鼓包漏液** —— 放电机解决不了起火风险。这是全系统唯一一道
失败后果是**起火**而不是**数字算错**的闸。

### 3c · 今天一道工序都不受理的安全状态

**恰好一个:`water_exposed`(进过水)。**

本刀之前是两个(`water_exposed` 与 `swollen_leaking`);R4 解决了后者。

`water_exposed` 留着**不是遗漏**,是同一条处置:它可能在干燥后可投,
而**那是一个判断,等一次裁定,不等一个猜测**。fixture 160 F7 把这个集合钉死 ——
多一个 = 院子里有一种料没有去处而没人说;少一个 = 有人在没有裁定的情况下
替那种料开了一条路。
