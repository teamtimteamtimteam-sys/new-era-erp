## 1 · ★★★ 闸轮与探针改了什么 —— 三个发现,而一个改掉了这一刀的代码

### ★★★ G1 · `qty.render` 一个像素都渲染不到 —— **而第一版判据说它是绿的**

Tim 的 Q5 裁的是**「那句告警在 390px 上留在零次点按」**。落地写的是
「同时进 `render` 与 `edit`」,理由看起来很硬:`page-owned` 下 `editing` 恒为真,
于是 `render` 只在手机那一行上画得到 —— **那句话对【priority 的列】成立,而数量不是。**

| | |
|---|---|
| **机制** | `editable-table.tsx:819` 给**非 priority** 的列挂的是 `hidden sm:table-cell` —— **整个 `<td>` 在 390px 上 `display:none`**。里面那个 `<span className="sm:hidden">{c.render(row)}</span>` 跟着一起不画。 |
| ★★★ **判据为什么绿** | 第一版读的是 `td.textContent` —— 而 **`textContent` 不认 CSS**。它把桌面那一份(`hidden sm:block` 的 `edit()`)也读了进来,于是那句话读回来**两遍**,正则当场命中。**一条证明「它在 DOM 里」的判据,冒充了一条证明「它在屏幕上」的判据。** |
| ★ **怎么被抓到的** | 收紧判据,单独问一次「屏幕上有几份」。第一版收紧用的是 `offsetParent !== null` —— **读回 0**,与 `innerText` 读得到那句话**直接打架**。☞ 逐项量下来才看清:`display:none` 的是**整格**,于是 `innerText` 退化成 `textContent`。 |
| ★ **最后的判据** | **直接问几何**:`getBoundingClientRect().height > 0`。一个不占位置的元素,在屏幕上就是没有。 |
| ★★ **改法** | 那句告警搬进**行号那一格的叠加块**(与【已收】同一处,`#22` 同形);`qty.edit` 里那一份照旧(桌面就地编辑 + 手机展开区各一份)。**实测:那一行上屏幕 1 份 / DOM 2 份。** |

> ### ☞ 判词
> ★★★ **`offsetParent` 与 `getComputedStyle(el).display` 都答不了「屏幕上有没有」。**
> 前者答的是「有没有一个定位祖先」;后者更险 —— **`display:none` 不会传到子元素的
> 计算值上**,所以 `display:none` 里面的 `<p>` 读回来照样是 `block`。
> ☞ **本仓库为「一个读 DOM 的判据要说清它认的是哪一层」付过第六次账**
> (DRAFT-6 的探针一口气付了六次)—— 而这一次是**第一次它把【产品】也拖了出来**。

### ★★ G2 · 第三块承重注释,而它是**这一刀主动违反的那一条**

委托书点名两块(`:165-179` PUR-1 · `:309-311` 两个隐藏输入,两个行号都核对无误)。
★ 第三块是 `:137-152` 的 `TABLE-PHONE-4` 抬头,它的 ★★ 段逐字写着:

> `line_price_status` 是三条【并列数组】……折叠一列是用 CSS 藏,【藏起来的 input
> 照样提交】—— 画两遍就是每行往数组里多塞一格,整组配对当场错位。

☞ **而这一刀把那三列全部折走了。** 与另外两块的区别要紧:
那两块**不再描述一条活着的约束**;这一块**说的是一条这一刀正在违反的规矩**。

### 2.2 ★★ `null` 与 `[]` —— **分开它们的是勾选框,不是那座桥在不在**

`terms_json` **无条件渲染**,而 `actions.ts` 先看 `edit_terms`:没勾就**一个字都不读它**。
⚠ **把它画进 `{editTerms && …}` 里会得到一个安静的坑**:勾上→改几期→取消勾选→提交,
那一刻桥被卸载,`formData.get('terms_json')` 变成 `null`。
**今天不会发作**(没勾就不读),而它让两条路**互相依赖** ——
正是「两份判断在写下的那天一致、此后各自漂移」的形状。

### 2.3 ★★ 四条承重行为逐字节搬,而 SQL 那一侧证明了其中两条是**机械上**承重的

| 裁定 | 落点 | ★ 它为什么不能被"顺手整理" |

### 2.4 ★ `TermRow = { uid, term }` —— **没有剥离动作**

uid 放在那一期**旁边**,桥写的是 `x.term`。☞ **不是"记得剥掉 uid",是它根本不在那个对象里。**
形状与 `NewOrderForm.tsx:158` 的 `TermLine` 逐字同源;
★ 计数器而不是 `crypto.randomUUID()`(服务端渲染与客户端水合两侧要给出同一串值),
而进门那几期的 uid 是**确定的** `t0 … tn-1`,计数器从它们之后起跳。

★★ **Tim 的 Q6:桥上那个 `seq` 照送不剥,而 `actions.ts` 保留 `seq: i + 1`。**
⚠ 照直记一句:页面上那个 `AmendTerm.seq` **删一期之后不重排、加一期用 `ts.length + 1` 会撞号**,

**「它是读出来的,不是用来算的」**。一个陈旧、可见、又被静默丢弃的字段,
正是下一个人会「顺手整理」成缺陷的那种东西。

### 3.1 ⚠ 证据的两半,强度不一样,所以分开记

| | |
|---|---|
| ★ **「键送出去了」—— 量到了** | 探针实测桥上带着 `line_no: 1` |
| ⚠ **「拒绝从此点对了行」—— NOT MEASURED** | 线上造不出:只读清点(**`psql` 直连,`current_user = postgres`,`rolbypassrls = t`,三张全是基表 `relkind 'r'`** —— 所以这个数是真行数)**五张可改的单,每一张都只有 1 行**。☞ 一行的单上,「点名的是哪一行」**说不出对错**;要证明它点错了行,得有第二行。**而委托书禁止建数据。** |

### 3.2 ★★ 它为什么活到今天 —— **在册的那条登记写着一句反话**

☞ ★ **它是怎么写错的,值得记一句:** 它是从「采购的消息模板里有 `line_no` 这个位置」
推出来的,**而没有人去看那一侧【送不送】它** —— 一个关于**消息模板**的事实,

☞ ★★ **一条错的登记比没有登记更贵:它替下一个人把怀疑花掉了。**
