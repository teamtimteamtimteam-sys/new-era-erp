### 2.2 ★★ `#15` / `#16` —— **两座桥,而服务端靠 `alloc_kind` 分辨**

搬家前两张表**共用三条并列数组**,按下标配对;而 `direction === 'out'` 时
**两张表同时渲染**(实测:`#15` 2 行 · `#16` 8 行),于是那三条数组里是两张表的行接在一起。

☞ **而 `actions.ts` 那段循环逐行读的是 `allocKinds[i]`** —— **它本来就按 `kind` 分辨,
不按位置**。所以两座桥在服务端**先拼起来,再原样走同一个循环**:
★★ **那段判据一个字都没改**,而每一行自己带着自己的 `kind`。

★ **分成两座的理由在【页面那一侧】**:两张表的列不是同一组,合成一个联合数组
会让一半的列在另一半上没有意义 —— 与 `#22`/`#23` 同一条裁定。

## 3 · ★★★ 两次误判,照直记 —— **它们比这六张表更值钱**

### 3.1 ★★★ 我把三张视图读成了空的,而空的是【我的判据】

开工前我用 Management API 清点 `#15`/`#16`/`#13` 的源,三张视图
(`po_prepayment_applicable` · `ap_open_items` · `ar_open_items`)**全是 0 行**。
☞ 于是我把**委托书点名的重点证明**(「两表各填一格 → 两座桥各一行 → `kind` 正确」)
整臂改写成了「源是空的,NOT MEASURED」,**并且已经跑过一轮**。

★★ **浏览器里带着真会话一看:`#15` 2 行、`#16` 8 行 —— 它们一直在那儿。**

**成因量出来了,一行 SQL:**

```
gated_po / gated_ap / gated_ar = true  ← 三张视图都带 has_permission() 谓词
auth.uid() is null = true · current_user = postgres  ← Management API 没有 JWT
```

☞ `has_permission()` 是 `SECURITY DEFINER`,解析的是 `auth.uid()`;
**没有 JWT,谓词恒假,视图对它恒空 —— 与线上有没有数据【无关】。**

> ### ☞ 判词
> ★★★ **一个「0 行」的读数,先问它是【谁】读的。**
> 这与本仓库那条「先问这个判据读的是哪一份真源」是同一条,而这一次它的形状更险:
> **那个零看起来像一次测量,而它其实是一次【权限拒绝】** ——
> 两者在 `[]` 这个字节上长得一模一样(`mustRows` 那条法则的第 N 张脸)。
> ☞ **而它差一步就把一件【证得了】的事写成了「证不了」** ——
> 一份说「NOT MEASURED」的报告读起来很诚实,**而它这一次会是假的**。
